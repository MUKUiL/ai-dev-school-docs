# 仕込んだ欠陥の一覧（運営用・受講生には見せない）

> **この文書は解答です。** `1-2-7`（UI のデバッグ）と `1-2-8`（テストの基本テクニックと注意点）で使う欠陥仕込み版の中身。
> 受講生に配る際は、このファイルを除いて配布してください。
>
> - 作成日：2026-08-07 ／ 元にしたコード：`../02-nextjs/`（欠陥なしの完成形）

## 設計の意図

**3つの欠陥のうち、2つはテストが捕まえ、1つは捕まえません。** これが `1-2-8` の「緑＝完了ではない」（Constitution 第13条8）の実例になります。

`npm test` を実行すると **7 failed / 16 passed** になります。テストを全部緑にしても、**欠陥③は残ったまま**です。

| # | 欠陥 | 種類 | `npm test` で | 気づく方法 |
| --- | --- | --- | --- | --- |
| ① | カウンタが完了を数えている | ロジック | **落ちる** | テスト or 画面を見る |
| ② | 前後の空白を落としていない | ロジック | **落ちる** | テスト or 空白を入れてみる |
| ③ | 長い ToDo がはみ出す | 表示 | **通る** | **実際に長い文字を入れて見るしかない** |

---

## ① カウンタが「完了」を数えている

**ファイル**：`lib/todos.ts` の `countLabel`

```ts
// 仕込んだ状態
const remaining = todos.filter((t) => t.done).length;

// 正しい状態
const remaining = todos.filter((t) => !t.done).length;
```

**症状**：「未完了 N 件」の N が、実際には完了した件数になっている。1件も完了していないときは「未完了 0 件」と出る。

**なぜ気づきにくいか**：ToDo が0件のときと、全部完了しているときは、正しい実装と同じ表示になる。**試し方によっては見逃す。**

**落ちるテスト**
- `todos.test.ts` → `countLabel（F-4 件数の表示）` の「未完了と全体の件数を出す」「全部完了しているとき」
- `TodoApp.test.tsx` → `F-4 件数を表示する` の「追加・完了・削除のたびに更新される」

## ② 前後の空白を落としていない

**ファイル**：`lib/todos.ts` の `createTodo`

```ts
// 仕込んだ状態
if (text === "") return null;
return { id: newId(), text: text, done: false };

// 正しい状態
const trimmed = text.trim();
if (trimmed === "") return null;
return { id: newId(), text: trimmed, done: false };
```

**症状**：スペースだけを入れて「追加」を押すと、**中身が空に見える行が増える**。前後に空白を含む入力もそのまま保存される。

**受け入れ基準との対応**：要件 F-1 の「空文字と空白のみは追加されない」に違反している。

**落ちるテスト**
- `todos.test.ts` → `createTodo（F-1 追加）` の「前後の空白を落とす」「空白だけも追加しない」
- `TodoApp.test.tsx` → `F-1 ToDo を追加する` の「空白だけのときは追加されない」、`F-5` の「保存済みのデータが最初から表示される」（連鎖して落ちる）

## ③ 長い ToDo がはみ出す【テストでは捕まらない】

**ファイル**：`app/globals.css`

```css
/* 仕込んだ状態 */
.todo-item .text {
  flex: 1;
  white-space: nowrap;
}

/* 正しい状態 */
.todo-item .text {
  flex: 1;
  word-break: break-word;
}
```

**症状**：スペースを含まない長い文字列（URL や長い英単語など）を入れると、**行が横にはみ出し、「削除」ボタンが画面の外へ押し出される**。

**再現手順**
1. 入力欄に次を貼り付けて追加する
   `https://example.com/very/long/path/that/keeps/going/and/going/and/going/forever`
2. 「削除」ボタンが右に押し出され、押せなくなる

**なぜテストが捕まえないか**

このテストは jsdom（ブラウザではない環境）で動いています。**jsdom はレイアウトを計算しません。** 幅・折り返し・はみ出しといった「見た目」は、テストからは見えないのです。

`npm test` はこの欠陥について**何も言いません**。緑のままです。だから――

> **テストが全部通ることは、「壊れていない」ことの証明ではありません。**
> テストが通ったのは、**自分が書いた観点だけ**です。書かなかった観点は、誰も見ていません。

これが `1-2-8` の中心的なメッセージです。

**では、どうすれば気づけるか**

| 方法 | できること | できないこと |
| --- | --- | --- |
| 手で触る | 長い文字を入れれば見つかる | 毎回やるのは現実的でない |
| ブラウザを動かすテスト（E2E） | 実際の描画に近い形で確かめられる | 用意と維持のコストが高い |
| 見た目の差分を撮って比べる | 崩れを機械的に検出できる | 「何が正しいか」は人が決める必要がある |

`1-2-8` では**手で触って見つける**ところまでを扱います。自動化は Phase 3（`3-3-9` 単体テストと統合テスト）で扱います。

## 受講生への出し方

| 節 | 使い方 |
| --- | --- |
| `1-2-7` UI のデバッグ | **欠陥の数を伝えずに**渡し、症状から原因を突き止めさせる。エラーが出ない種類のバグなので、「動いているのに何かおかしい」の探し方を扱う |
| `1-2-8` テストの基本テクニックと注意点 | `npm test` を先に実行させ、**7件落ちること**を確認 → 直す → **全部緑にしてから、まだ③が残っていることに気づかせる** |

**②→①→③ の順に見つかりやすい**です。③にたどり着かないまま「直った」と判断するのが、この演習でいちばん起きてほしい失敗です。
