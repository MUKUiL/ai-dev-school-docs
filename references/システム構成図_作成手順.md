# システム構成図の作成手順（6ステップ）

> **このファイルの位置づけ**：要件定義書の「5. システム構成図」を書くときの**手順書**です。
>
> **関連資料**
>
> - 要件定義書テンプレート：[`要件定義書_フォーマット.md`](./要件定義書_フォーマット.md)（§5 に図の置き場所）
> - 記入例（Mermaid 付き）：同テンプレート §5-1〜5-5
>
> **使い方**：下の6ステップを**上から順に**進めます。各ステップの「完了条件」を満たしてから次へ進んでください。

---

## 全体のポイント

**見る人が初めてでも「このシステムはこう動くんだな」と直感的に理解できる構成にすること。**

- 図は**装飾ではなく合意の道具**です。読み手が「どこに何があり、何がどこへ流れるか」を一目で追えるかが基準です。
- 最初から細部を描かず、**Step 1 → 6 の順で情報を足していく**と破綻しにくくなります。
- 図だけで伝えきれない前提・制約・未決事項は、**Step 6 の説明文**に必ず書き残します。

---

## Step 1. 概要を描く

**システム全体の構成をざっくり俯瞰します。**利用者、インターフェース、中心となる処理を配置します。

### やること

1. 用紙（または Mermaid の `flowchart`）の**左または上**に「利用者」を置く
2. その右（または下）に**利用者が触る入口**（ブラウザ、管理画面、モバイルアプリ等）を1つ置く
3. 中央に**このシステムの核**（Web アプリ、API、バッチ等）を1ブロックで置く
4. まだモジュール分割はしない。**3〜5個の箱**に収まる粒度にする

### この段階で書くもの（例）

```
利用者 → ブラウザ（UI） → アプリケーション → （外部は Step 5 で足す）
```

### 完了条件

- [ ] 「誰が」「何を触って」「どこに届くか」が3要素以内で説明できる
- [ ] 機能一覧（F-1, F-2…）の詳細は**まだ書いていない**
- [ ] 初見の人に30秒で見せて、大枠の流れが伝わる

### よくある失敗

- 最初から DB や LLM まで全部描いて、視線の流れが分からなくなる
- 「システム」の箱の中身が空で、何を担当するか不明

---

## Step 2. モジュールを定義する

**機能単位でブロック化して整理します。**何をどこで担当するのか明確にします。

### やること

1. 要件定義書の**機能要件（F-1, F-2…）**を一覧にする
2. 各機能を**1つのモジュール（箱）**に対応させるか、関連機能を**1モジュールにまとめる**か決める
3. 各モジュールに**短い名前と1行の役割**を付ける（例：`検索モジュール` ── 関連文書断片を返す）
4. Step 1 の「アプリケーション」を、**モジュールの集まり**に置き換える

### モジュール定義表（作成用）

| モジュール名 | 担当する機能 | 入力 | 出力 | 備考 |
| --- | --- | --- | --- | --- |
| 〔例：UI〕 | 質問表示・回答表示 | ユーザー操作 | HTTP リクエスト | フロント |
| 〔例：API〕 | オーケストレーション | HTTP | JSON 応答 | Route Handler |
| 〔例：検索〕 | F-2 文書検索 | 質問ベクトル | 断片リスト |  |
| 〔〕 | 〔〕 | 〔〕 | 〔〕 | 〔〕 |

### 完了条件

- [ ] 要件の各機能が、**どれか1モジュールの責務**として書ける
- [ ] モジュール名だけ見て、**何を担当するか**が分かる
- [ ] 「この機能、どの箱？」と聞かれたときに迷わない

### よくある失敗

- 画面1枚＝モジュール1個にして、箱が多すぎる
- 逆に「アプリ全部」1箱のまま Step 3 に進む

---

## Step 3. モジュールの関係を描く

**各機能ブロック間のデータフローや依存関係を矢印などで表します。**

### やること

1. Step 2 で決めたモジュールを図上に配置する
2. **主要な利用シナリオ1本**（例：質問して回答を得る）を選び、矢印でつなぐ
3. 矢印には**何が流れるか**をラベルで書く（例：`質問文`、`断片`、`回答 JSON`）
4. **依存の向き**を統一する（通常：利用者 → UI → API → 下位モジュール → 外部）

### 矢印の書き方

| 種類 | 表現 | 例 |
| --- | --- | --- |
| 同期呼び出し | 実線矢印 | UI → API |
| データ参照 | 矢印＋ラベル | API → DB：`検索` |
| 外部送信 | 点線または別色 | API ⇢ LLM API |

### 完了条件

- [ ] 代表フロー1本を、図だけで**左から右（または上から下）**に追える
- [ ] 双方向に矢印が乱立していない（必要なら「応答」矢印を別途）
- [ ] 循環参照がある場合、**意図的か**説明できる

### よくある失敗

- 矢印にラベルがなく、「何のデータか」が分からない
- すべての機能を1枚に描こうとして、読めなくなる → **代表フローは1本に絞る**

---

## Step 4. ハードウェアを配置する

**サーバー、ネットワーク、端末など、物理的な構成も含めて表記します。**

### やること

1. **利用者の端末**を明示する（社内 PC、スマートフォン、タブレット等）
2. **アプリの実行場所**を書く（例：Vercel、自社サーバー、コンテナ）
3. **データの置き場所**を書く（例：Supabase、S3、オンプレ DB）
4. 必要なら**ネットワーク境界**を書く（社内 VPN、ファイアウォール、インターネット）

### このコースでの書き方（PaaS / BaaS 中心）

| 論理 | 物理・インフラでの表現 |
| --- | --- |
| フロント | Vercel（Edge / CDN） |
| API | Vercel Functions |
| DB | Supabase（マネージド PostgreSQL） |
| 利用者 | ブラウザ（端末は社内 PC 等） |

> **細かい機器名まで描かなくてよい**場合もあります。ただし「どこで動き、どこにデータがあるか」は必ず図または説明文に残します。

### 完了条件

- [ ] 「本番ではどこで動くか」が図から読み取れる
- [ ] データが**どのサービス／リージョンに残るか**が分かる
- [ ] 社内限定公開など、**ネットワーク上の制約**があれば境界として書いてある

### よくある失敗

- クラウドの箱だけ並べ、利用者の端末が消える
- 「サーバー」と1語で済ませ、実際はサーバーレスなのに誤解を招く

---

## Step 5. インタフェースを示す

**外部サービスとの連携、API やデータベースとのやり取りなども忘れず記載します。**

### やること

1. **外部 SaaS / API** を図の外側に置く（LLM、決済、メール送信等）
2. **自システムとの境界**（API エンドポイント、Webhook、バッチ連携）を明示する
3. **送るデータ・送らないデータ**を要件定義書 §4-3 と突合する
4. DB とのやり取りは、**読み取り／書き込み**を区別してラベルする

### インタフェース一覧（作成用）

| 連携先 | 方向 | プロトコル／形式 | 送るもの | 送らないもの |
| --- | --- | --- | --- | --- |
| 〔例：Anthropic API〕 |  outbound | HTTPS / JSON | 質問、断片 | 個人情報、給与 |
| 〔例：Supabase〕 |  bidirectional | SQL / REST | ベクトル、メタデータ | 〔〕 |
| 〔〕 | 〔〕 | 〔〕 | 〔〕 | 〔〕 |

### 完了条件

- [ ] 外部連携が**すべて図上に1つ以上の箱**として現れる
- [ ] API キーが**フロントに載らない**構成が図から読み取れる（該当する場合）
- [ ] 要件定義の「外部連携一覧」と**項目が対応**している

### よくある失敗

- LLM だけ描いて、DB やストレージの IF が抜ける
- 「外部 API」とだけ書き、**どのタイミングで呼ぶか**が Step 3 のフローと一致しない

---

## Step 6. 図の説明文を添える

**最後に、図に書ききれなかった前提や補足をテキストで記述します。**構成図だけでは伝わらない部分を補います。

### やること

1. 図の**下または横**に、次の項目を短い箇条書きまたは表で書く
2. 図の**凡例**（記号・色・線種の意味）があれば記載する
3. **未決事項**（認証方式、公開範囲等）は「未決」と明記し、決定期日を書く

### 説明文に含める項目

| # | 項目 | 書く内容 |
| --- | --- | --- |
| 1 | 図の目的 | この図が表すスコープ（初版／全体 等） |
| 2 | 前提 | 利用環境、対象ユーザー、初版で含まないもの |
| 3 | 代表フロー | Step 3 で選んだシナリオを文章で再説明 |
| 4 | セキュリティ | 鍵の置き場所、ログに残さないデータ |
| 5 | 未決・将来 | Step 4・5 で省略したものと理由 |

### 説明文の例（抜粋）

> 本図は初版（社内限定・ログインなし）の構成です。利用者は社内 PC のブラウザからアクセスします。質問文と検索に使う文書断片のみ LLM API に送信し、給与・人事評価に関する文書は取り込み対象外です。Google Drive 自動同期は初版スコープ外で、文書更新は管理部による手動再取り込みとします。

### 完了条件

- [ ] 図を見ていない人が、説明文だけで**おおまかな動き**を復述できる
- [ ] 図と説明で**矛盾**がない（モジュール名・矢印・外部サービス名が一致）
- [ ] 要件定義書 §5 の各小節（5-1〜5-5）に、図または説明が**1つ以上**対応している

### よくある失敗

- 図だけ提出して、初版スコープ外の機能が含まれていると誤解される
- 説明が図の写し絵だけで、**前提・制約・未決**が書かれていない

---

## 6ステップ完了チェック

| Step | 確認 |
| --- | --- |
| 1 概要 | 利用者・入口・中心処理が俯瞰できる |
| 2 モジュール | 機能と箱の対応が明確 |
| 3 関係 | 代表フローのデータ流れが矢印で追える |
| 4 ハードウェア | 実行場所・データ置き場・端末が分かる |
| 5 インタフェース | 外部・DB 連携が漏れなく記載 |
| 6 説明文 | 前提・制約・未決がテキストで補完されている |
