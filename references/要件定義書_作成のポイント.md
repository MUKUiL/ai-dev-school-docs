## この資料で扱うこと

要件定義書は「何を・誰のために・どこまで作るか」を**合意する文書**です。設計・実装の正本ではありませんが、以降の工程が立ち返る**判断の根拠**になります。

| 章 | 主な問い |
| --- | --- |
| 概要 | なぜ今作るのか。用語の意味は揃っているか |
| 業務要件 | 業務はどう流れ、どれくらい・いつ・何をもって良しとするか |
| 機能要件 | システムは何をするか。合否はどう測るか |
| 非機能要件 | 速さ・安定・拡張・使いやすさはどこまで求めるか |
| セキュリティ | 何を守り、誰が触れ、どう検証するか |

## ドキュメントのバージョン管理

要件定義書は**合意のスナップショット**です。ヒアリングの結果が変わったり、スコープを切り直したりするたびに版を上げます。「最新版がどれか」が分からない状態は、手戻りの温床です。

### 履歴表の例

| 版 | 日付 | 変更概要 | 作成／更新 |
| --- | --- | --- | --- |
| 0.1 | 2026-07-10 | 初版ドラフト（ヒアリング反映） | 受託側 高橋 |
| 1.0 | 2026-07-22 | 総務部承認。外部送信一覧を追記 | 佐藤（窓口）承認 |

### 運用上の5点

1. **版番号のルールを決める**  
   例：`メジャー.マイナー`（`1.0`＝承認版、`1.1`＝軽微修正、`2.0`＝スコープ変更）。チーム内で意味を固定する。

2. **変更内容を残す**  
   「何を」「いつ」「誰が」変えたか。障害や認識齟齬のとき、どの版を前提にしていたか追えるようにする。

3. **正本の置き場所を1つにする**  
   メール添付・個人 PC・共有フォルダに散らばると、古い版を引用しやすい。Git リポジトリや共有ドライブの**決めたパス**に置く。

4. **変更には承認を挟む**  
   口頭修正の積み重ねは合意の形骸化を招く。窓口（発注側）の承認またはレビュー記録を残す。

5. **退避を習慣化する**  
   誤削除・上書きに備え、リポジトリのタグ付けや定期バックアップをセットにする。

## 1. 概要

プロジェクトに関わる人が、立場や専門性が違っても**同じ絵を見ている**状態をつくる章です。ここが曖昧だと、機能要件以降すべてが解釈ゲームになります。

### A. 背景

依頼文に書いてあること＝本当の課題、とは限りません。表面的な要望の奥にある**困りごと**と**組織として得たい結果**を言語化します。

**背景を書く4つの視点**

| 視点 | 書くこと |
| --- | --- |
| 関係者とのすり合わせ | 目的・課題を対話で揃え、誤解が残っていないか確認する |
| 現状の具体化 | 「何が起きているか」を事実ベースで。可能なら計測値を添える |
| 目指す状態 | 導入後にどうなっていればよいか。定性的でもよいが、数値があると議論が進む |
| 背景と要件の対応 | どの課題が、どの機能・非機能に結びつくか一行で示す |

**記述例（本コース題材に寄せた書き方）**

| 項目 | 内容 |
| --- | --- |
| 困りごと | 社内ルールの確認に、フォルダ探索で平均7分、Slack 待ちで25分かかっている（1週間・31件の実測） |
| 影響 | 総務部・在籍の長いメンバーへの聞き返しが増え、本業を圧迫している |
| 目指す状態 | 根拠つきで回答が返り、同種の Slack 問い合わせを**3割減**（6か月後を目安） |
| 対応関係 | 探しに時間がかかる（背景）→ 質問に答える検索機能（機能要件） |

### B. 用語定義（Glossary）

プロジェクト内で繰り返し出る語・略語は、**この章で一度定義**します。読者が別部署・別業界でも、同じ意味で読めるようにします。

記入例
| 用語 | 定義 |
| --- | --- |
| RAG | 関連文書を検索してから生成する構成。回答の根拠を示しやすい |
| 断片（チャンク） | 長い文書を検索しやすい長さに分割した単位 |
| 根拠 | 回答の根拠となった社内文書への参照。ファイル名だけでは不十分な場合がある |
| 外部送信 | 自社管理外の API・SaaS にデータを渡すこと。対象と禁止データを一覧化する |

> 定義文自体が曖昧だと、設計・実装・テストで解釈が割れます。**1文で判定できる**粒度を目指します。

## 2. 業務要件

「業務を回すうえで、システムに何を求めるか」を整理する章です。画面や API の話の前に、**業務の流れ・量・時間・評価軸・範囲**を固定します。

### A. 業務フロー

誰が・いつ・何を・どの順で行うかを、**1枚の図**で共有します。

**フロー図を作る手順**

1. 対象範囲の開始点と終了点を決める（例：問い合わせ発生〜回答確認まで）
2. 作業ステップを洗い出し、順序を固定する
3. 開始／処理／判断／終了など、基本記号で箱と矢印に落とす
4. 担当者ごとにレーン（スイムレーン）を分ける
5. 繰り返し・分岐は矢印と菱形で表す
6. 図だけでは伝わらない例外は、脚注または説明文に書く

**ポイント**：初見の読者が**業務の全体像**を30秒で掴めるかが目的です。複雑な業務ほど図の効果が大きいです。

### B. 規模（スケール）

過小見積もりは性能不足、過大見積もりは無駄なコストです。ざっくりでも**数量のオーダー**を書きます。

| 項目 | 記入例（題材により変える） |
| --- | --- |
| 利用回数 | 1日 25〜40 回（ピーク 60 回） |
| 同時利用 | 最大 15 セッション程度 |
| 対象データ | 現役文書 35 ファイル前後、総文字数 35 万字規模 |
| 利用者 | 全社 約300名（うち heavy user は数十名） |

※ 業務フロー図の各ステップ横に「件数／頻度」を書いてもよいです。

### C. 時期・時間（スケジュール）

業務の**ピーク**と**締切**は設計に効きます。リアルタイムが要るか、日次バッチで足りるかの判断材料になります。

- フロー図に「発生タイミング」「おおよその所要時間」を足す
- 文章で補足する（例：「月初の経費問い合わせが集中する」）
- 日次・週次・月次の定期処理があれば表にまとめる

### D. 指標（KPI）

**成功したかどうか**を後から説明するための物差しです。指標がないと「なんとなく良くなった」で終わり、投資対効果を語れません。

**要件定義段階で KPI を書く理由**

| 効果 | 説明 |
| --- | --- |
| 成功の定義を共有 | 発注・開発・利用部門が同じ数字で「できた／できていない」を話せる |
| 優先順位の根拠 | 「その機能はどの指標を動かすか」で要否を議論できる |
| 改善の起点 | 導入前の数値（ベースライン）があれば、導入後の差分が測れる |

> **鉄則：目標値だけでなく現状値をセットで書く。** 現状が分からなければ達成度は測れません。

**指標の例（業務・システム一般）**

| 指標 | 意味 | 測り方の例 |
| --- | --- | --- |
| 処理時間 | 1件あたりの作業時間 | 開始〜完了時刻の差 |
| リードタイム | 依頼から完了まで（待ち時間含む） | タイムスタンプの差分 |
| スループット | 単位時間あたりの処理件数 | ログ集計 |
| エラー率 | 失敗・不備の割合 | エラー件数 ÷ 全件数 |
| 手戻り率 | やり直しの割合 | 差し戻し ÷ 全件数 |

**KPI を決める流れ**

1. ゴールを言葉にする（速くしたい／ミスを減らしたい 等）
2. 目的に対応する指標を**3〜5個**に絞る
3. **ベースライン**を計測または推定で記録する
4. 目標値と期限を書く
5. **どこから・どう取るか**（ログ、ヒアリング、アンケート）を決める

**目標設定の例**

| 指標 | 現状 | 目標 | 期限 | 取得方法 |
| --- | --- | --- | --- | --- |
| ルール確認の所要時間 | 中央値 7分 | 3分以内 | 稼働4か月後 | 利用ログ＋アンケート |
| Slack への同種質問 | 週 18件 | 週 12件以下 | 稼働6か月後 | チャンネル投稿数 |
| 根拠なし回答の許容 | ─ | 0件（根拠必須） | 初版リリース時 | 仕様レビュー |

| 悪い例 | 良い例 |
| --- | --- |
| 「業務効率を上げる」 | 「ルール確認の所要時間を中央値7分から3分以内に下げる（4か月後）」 |

**測れる設計に織り込む**

KPI を決めたら、ログ・集計・ダッシュボードなど**データが残る要件**を機能／非機能側にも書きます。運用後の PDCA が回りやすくなります。

### E. 範囲（スコープ）

**対象／対象外**を明示し、認識ズレと無秩序な追加要望を防ぎます。

- **対象**：例「就業規則・経費・開発ガイド等、総務部が選定した現役文書」
- **対象外**：例「給与・人事評価フォルダ」「Google Drive 自動同期（初版）」
- **境界**：外部 API・既存 SaaS との接点。自システムが担う範囲と、人が担う範囲

## 3. 機能要件

システムが**何をするか**を、設計・実装・テストが参照できる形で書きます。

### A. 機能一覧と分類

機能を階層（大→中→小）または **F-1, F-2…** のように番号で整理し、抜け漏れを減らします。

**各機能に書くこと**

| 項目 | 内容 |
| --- | --- |
| 概要 | 何をするか |
| 入力・処理・出力 | 第三者が再現できる粒度 |
| 利用シナリオ | 誰がどう使うか（任意だが有効） |
| 受け入れ条件 | **合否が判定できる**記述 |

> **AI 駆動開発では受け入れ条件が特に重要です。** 曖昧な説明でもそれらしい実装が速く量産されるため、**ユーザー・レビュアー・テストが同じ合否**になる水準を目指します。

**受け入れ条件の例（質問応答）**

| 区分 | 例 |
| --- | --- |
| 弱い | 「質問に答えられること」 |
| 強い | 根拠となる断片が無いときは回答を生成せず、理由を表示すること／根拠文書へのリンクを必ず付けること |

### B. 画面仕様

詳細な UI 設計の前に、**どんな画面が必要か**を一覧にします。

| 画面ID | 名称 | 役割 |
| --- | --- | --- |
| SCR-01 | 質問入力 | 自然文で問い合わせる |
| SCR-02 | 回答表示 | 回答本文と根拠を示す |
| SCR-03 | 文書管理 | 取り込み・再取り込み（運用者向け） |

画面遷移図は任意ですが、操作の流れが複雑なら早期に描くと認識が揃います。

### C. 情報・データ・ログ

| 観点 | 書くこと |
| --- | --- |
| データ | 主要エンティティ、属性、制約（ER 図など） |
| データフロー | どの処理が何を読む／書くか |
| ログ | 種類、記録項目、保持期間。**本文・個人情報を載せない**方針 |

### D. 外部インターフェース

| 項目 | 例 |
| --- | --- |
| 一覧 | 連携先、目的、形式（REST／CSV 等） |
| 詳細 | 項目、必須、認証、エラー時の再送・通知 |
| 送信境界 | 送ってよいデータ／送らないデータ |

要件定義書は詳細設計の入力になります。**早い段階で開発・テスト・利用者とレビュー**し、合意を取ることを推奨します。

## 4. 非機能要件

「見えにくい品質」── 性能、信頼性、拡張性、使いやすさなど。機能が動いても、ここが欠けると離脱や障害につながります。初期段階で明文化すると、見積もり精度とリスク管理に効きます。

### A. ユーザビリティ・アクセシビリティ

- 対象ユーザー（IT 習熟度、利用端末、制約の有無）を定義する
- 操作目標（例：主要操作は**4クリック以内**）を書く
- キーボード操作、読み上げなど必要なら要件に含める

### B. システム方式（アーキテクチャ）

- Web／モバイル、クラウド／オンプレなどの方針
- 採用技術の概要（[`システム構成図_作成手順.md`](./システム構成図_作成手順.md) と整合）
- 冗長化・フェイルオーバーが要るか

### C. 規模（スケーラビリティの前提）

| 項目 | 記入例 |
| --- | --- |
| 同時接続 | 最大 20〜30 |
| 1日あたりリクエスト | 数百〜千件程度 |
| データ増加 | 年間で文書数 2倍まで想定 等 |

想定が粗くても、**オーダーが違うと設計が変わる**項目は書いておきます。

### D. 性能

- 応答時間の目標（画面表示、API、バッチそれぞれ）
- ピーク時の許容上限

### E. 信頼性

- 稼働率やメンテナンス窗口
- バックアップ頻度、RTO／RPO（必要なら）

### F. 拡張性

- 機能追加時にどこまで局所化できるか
- DB や compute のスケール方針

### G. 互換性

- データ形式・API のバージョニング方針
- 移行手順の要否

### H. 継続性（DR・BCP）

- 冗長構成、別リージョン、代替手段
- 監視とエスカレーション

### I. AI・LLM を使う場合の追加観点

従来の「3秒以内」だけでは足りないことがあります。**制御しきれない外部推論**を前提に書きます。

| 観点 | 要件に書くこと |
| --- | --- |
| レイテンシ | 初回応答までの許容時間、ストリーミング表示の要否 |
| コスト | 1回あたり・月間の上限、超過時の挙動 |
| 出力の揺らぎ | 再現性が要る処理は AI を使うか、パラメータ方針 |
| 誤回答 | 根拠が無いときの扱い、人の確認を必須にする範囲 |
| 可用性 | API 障害・レート制限時のフォールバック |

セキュリティ（プロンプトインジェクション、外部送信）は次章とセットで読みます。

## 5. セキュリティ要件

「守るルール」と「検証のしかた」を要件として固定します。

### A. 情報セキュリティ

- 情報の重要度区分（公開／社内限定／機密 等）
- ロールとアクセス範囲
- 認証方式、鍵・シークレットの置き場所（**フロントに書かない**）
- 通信・保存の暗号化方針
- 入力検証、WAF 等の要否

### B. 稼働環境

- 対応ブラウザ・OS（**固定バージョン列挙より**「サポート中の直近 N バージョン」など）
- EOL 環境を対象外とする方針
- 保証環境と非推奨環境の区分

### C. テスト（セキュリティ・品質）

| 種別 | 目的 |
| --- | --- |
| 機能テスト | 基本操作が仕様どおりか |
| 脆弱性診断 | 注入系などの代表パターン |
| 負荷・耐障害 | 想定ピークや障害時の挙動 |

合否基準、実施体制、ダミーデータ方針、ログ取得を**要件段階でドラフト**しておき、予算とスケジュールに載せます。

### D. AI・LLM 利用時のセキュリティ

| リスク | 対策の例 |
| --- | --- |
| プロンプトインジェクション | システム指示とユーザー入力の分離、出力の検証 |
| 機密の外部送信 | 送信可否一覧、マスキング、学習利用オプトアウトの確認 |
| 生成コードの脆弱性 | 人のレビューと静的チェックを必須化 |
| 権限を超えた出力 | 渡すデータを利用者権限で制限 |
| 監査 | 誰が何を入力し、何が返ったか（本文は最小限） |

AI 周辺の脅威は更新が速いです。OWASP LLM Top 10 等の**参照先と確認日**を添え、定期見直しを前提にします。

## 関連ドキュメント（テストまわり）

要件定義とあわせて、次の文書が後工程で登場します。最初から「作る／作らない」を決め、工数に含めるか検討してください。

| 文書 | タイミング |
| --- | --- |
| テスト方針・テスト計画 | 要件合意前後（ドラフト可） |
| テスト設計・ケース・データ仕様 | 設計〜実装 |
| 実行報告・不具合報告 | 検証〜リリース |
| セキュリティ診断報告 | 外部委託時 |
