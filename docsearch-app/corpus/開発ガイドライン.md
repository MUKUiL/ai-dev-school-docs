# 開発ガイドライン

> 株式会社テックバディ 情報システム部
> ※ 本書は架空の会社の架空の文書です。実在の企業・団体とは関係ありません。

## 1. このガイドラインについて

情報システム部で共通して守る決まりをまとめたものです。案件ごとの事情で変える場合は、案件の README に理由を書いてください。

## 2. ブランチ

### 2-1 ブランチ名の付け方

ブランチ名は `種別/チケット番号-内容` の形式とする。

| 種別 | 使う場面 | 例 |
| --- | --- | --- |
| `feature` | 機能の追加 | `feature/MS-123-add-search` |
| `fix` | 不具合の修正 | `fix/MS-456-null-check` |
| `hotfix` | 本番の緊急修正 | `hotfix/MS-789-login-error` |
| `chore` | 設定・依存の更新など | `chore/MS-234-bump-deps` |

内容は英小文字とハイフンで書く。日本語およびアンダースコアは使わない。チケット番号が無い作業は `chore/no-ticket-内容` とする。

### 2-2 マージ

`main` への直接のコミットは禁止する。マージはプルリクエスト経由で行い、マージ後はブランチを削除する。

## 3. コミット

### 3-1 コミットメッセージの書き方

1行目は50文字以内で、何をしたかを日本語の現在形で書く。末尾に句点は付けない。

```
検索結果の件数を上位3件に制限する
```

2行目は空行とし、3行目以降になぜその変更をしたかを書く。1行は72文字以内で折り返す。

複数の変更を1つのコミットにまとめない。1コミット1目的とする。

### 3-2 書いてはいけないこと

- API キー、パスワード、接続文字列
- 顧客名（案件コードで表す）
- 「修正」「対応」だけの本文

## 4. プルリクエスト

### 4-1 レビューの人数

プルリクエストのマージには、2名以上の承認を必要とする。うち1名は、当該プロダクトの担当経験がある者とする。

`hotfix` については、1名の承認でマージしてよい。ただしマージ後24時間以内に、もう1名のレビューを受けること。

### 4-2 プルリクエストに書くこと

- 何を変えたか
- なぜ変えたか
- 動作を確認した手順
- 影響範囲（触っていない範囲を明示する）

### 4-3 レビューの観点

レビューでは次を見る。指摘は「観点」と「具体的な箇所」をセットで書く。

- 要件を満たしているか
- 異常系が処理されているか
- テストが観点を尽くしているか
- 秘密情報が混ざっていないか

## 5. 依存ライブラリ

### 5-1 追加の手順

外部ライブラリを追加するときは、次の順で進める。

1. 既存の依存で実現できないかを先に確認する
2. 情報セキュリティ規程 第8条の手続きに従い、情報システム部の承認を得る
3. 承認後にプルリクエストを出す。プルリクエストの本文に、承認を得た申請番号を記載する
4. ロックファイルを必ずコミットに含める

### 5-2 選ぶときの基準

- 直近1年以内に更新されているか
- 既知の脆弱性が残っていないか
- ライセンスが業務利用を許しているか

## 6. テスト

単体テストと統合テストの両方を用意する。テストの観点は観点表に書き出し、テストで守れない範囲には代わりの確認手順を残す。

## 7. ドキュメント

設計の判断は ADR として `docs/adr/` に残す。1つの決定につき1ファイルとし、過去のファイルは書き換えず追記する。
