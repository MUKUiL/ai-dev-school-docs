# ADR-002: 生成は Anthropic、埋め込みは OpenAI を使う

| 項目 | 内容 |
| --- | --- |
| 状態 | 採用 |
| 日付 | 2026-08-09 |
| 関係する要件 | [requirements.md](../requirements.md) 4-2（外部連携）／3-2（費用・セキュリティ） |

## 決定

回答の生成は **Anthropic（Claude）**、文書と質問のベクトル化は **OpenAI の埋め込み API** を使う。2つのプロバイダのキーを、それぞれサーバー側の環境変数で管理する。

## 背景

- ADR-001 でベクトル検索を採用したため、埋め込みが必須になった
- **Anthropic は埋め込み API を提供していない**（最終確認日：2026-08-09）
- 生成側は Phase 2 から Claude を使っており、プロンプトの作り方・失敗の分類・ログ設計をそのまま継承できる
- クライアントの条件として「どの外部サービスに何を送るかを一覧にして提出する」があり、**送信先が増えることは提出物に影響する**
- **このとき分かっていなかったこと**：日本語の社内規程に対して、どの埋め込みモデルがどのくらいの精度を出すか。**比較して選ぶだけの材料が無かった**ため、実装例の多さと費用で選んだ

## 代替案

| 案 | 内容 |
| --- | --- |
| A | 生成も埋め込みも OpenAI に統一する |
| B | 埋め込みに Voyage AI を使う |
| C | ローカルの埋め込みモデルを使い、外部に送らない |

## 棄却理由

**A（OpenAI に統一）── 移行のコストに見合わない**

送信先が1つになる点は魅力だが、生成側を移すとプロンプト・失敗の分類・出力形式の検証をすべて作り直すことになる。**得られるのは「送信先が1つ減ること」だけ**で、要件のどれも改善しない。

**B（Voyage AI）── 判断材料が足りない**

Anthropic が案内している埋め込みのパートナーであり、Claude と組み合わせる前提の情報が揃う点は利点。ただし**日本語の実装例が OpenAI に比べて少なく、詰まったときに調べる材料が不足する。**現時点では、精度で上回るという確認が取れていない。

**この案を選ぶとしたら**：日本語での比較評価ができたとき、または Anthropic に統一する方針が立ったとき。

**C（ローカル埋め込み）── 実行環境の制約と、運用の複雑さ**

外部に文書を送らずに済むため、クライアントの条件1・2を大幅に軽くできる点は大きい。しかし Vercel Functions の実行時間とサイズの制約から、**ビルド時に索引を作る構成に限定される。**文書を1件直すたびに再デプロイが必要になり、要件（運用者が取り込み直せること）を満たしにくい。

**この案を選ぶとしたら**：外部送信が許可されなかったとき。**その場合は実行環境（ADR-001 の前提）から見直す。**

## 結果

**できるようになったこと**

- 埋め込みの費用が生成に比べて桁違いに安く、月額の目標に収まる
- 生成側の実装（プロンプト・異常系・ログ）を Phase 2 からそのまま持ち込める
- 実装例が多く、詰まったときに調べられる

**できなくなったこと・引き受けたリスク**

| # | 内容 | 対応 |
| --- | --- | --- |
| 1 | **管理するキーが2本になる** | 2本とも上限を設定する。どちらが失敗したかをログの `failureKind` で分ける |
| 2 | **送信先が2社になり、提出物が増える** | [notes/external-services.md](../notes/external-services.md) に一覧を作成済み |
| 3 | **障害の窓口が2つになる** | どちらが落ちているかを切り分けられるよう、失敗の分類をサービス単位で持つ |
| 4 | **埋め込みモデルを変えると全文書を再作成** | モデル名を設定の1か所にまとめ、変更時の作業範囲を明示する |
| 5 | 日本語での精度の比較ができていない | `3-3-8` の質問セット20問で実測する。**期待を下回ったら B を再検討する** |

> **5は「解決していない」項目として残す。**測る前に「十分だろう」と判断していない。
