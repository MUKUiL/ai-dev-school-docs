# ADR-001: 検索方式にベクトル検索を採用する

| 項目 | 内容 |
| --- | --- |
| 状態 | 採用 |
| 日付 | 2026-08-09 |
| 関係する要件 | [requirements.md](../requirements.md) 3-1 F-2・F-3／3-2 非機能 |

## 決定

質問に関連する文書の断片を**ベクトル検索**で取り出し、その断片だけを生成モデルに渡して回答を作らせる（案③）。キーワード検索との併用（ハイブリッド）は行わない。

## 背景

- 対象文書は約35ファイル・総計およそ350,000文字。**この時点で確認できているのはこの件数**で、将来の増加は「50ファイルまで」を上限として合意している
- 利用者は全社員約300名、1日20〜30回の利用を想定
- クライアントが求めているのは**ファイル名の一覧ではなく、根拠つきの回答**（[hearing.md](../hearing.md) Q3）
- 費用の目標は月額3,000円以内、上限設定が可能なこと
- **このとき分かっていなかったこと**：実際の質問がどのくらい文書の表記と一致するか。分割の大きさをどう取るのが適切か。**どちらも実装して測るまで分からないと判断した**

## 代替案

| 案 | 内容 |
| --- | --- |
| ① 全文渡し | 質問のたびに全文書をプロンプトに入れる |
| ② キーワード検索＋生成 | 質問から単語を取り出し、一致する文書だけを渡す |
| ④ ハイブリッド | ②と③を両方実行して結果を統合する |

## 棄却理由

**① 全文渡し ── 費用の要件（非機能4）が落ちる**

1日25回×全文分の入力が毎日発生し、月額3,000円の目標を大きく超える。あわせて、対象が50ファイルに増えたときに入力の上限に収まらなくなる可能性が高く、上限（要件で合意した50件）に対して余裕が無い。

**② キーワード検索＋生成 ── F-2 と非機能3 が落ちる**

ヒアリングで確認した実際の質問は口語で、文書側の表記と一致しない。「有給って何日繰り越せる」に対し、文書の表記は「年次有給休暇」「繰越」。キーワード一致では引けず、F-3（根拠が無いときは答えを作らない）が正常に動作した結果として「記載が見つかりません」が多発する。**機能としては正しく動くが、利用者にとって使えない。**

**この案を選ぶとしたら**：対象文書が型番・条項番号で引かれる性質のとき。

**④ ハイブリッド ── 解く問題が、この案件に存在しない**

④が補うのはベクトル検索の弱点（固有名詞・型番の完全一致）だが、対象は社内規程であり、型番や商品コードを引く用途が無い。統合の重み付けを決める作業と、2系統の索引を保守する手間が増える一方で、**それに見合う精度の向上が見込めない。**

**この案を選ぶとしたら**：対象に製品マニュアルや部品表が含まれるとき。

## 結果

**できるようになったこと**

- 言い換えを含む口語の質問から、該当する条項を引ける
- 根拠を断片単位で示せるため、F-2（示した根拠が実在すること）を機械で判定できる
- 質問1回あたりの入力が数千トークンに収まり、費用の目標に入る

**できなくなったこと・引き受けたリスク**

| # | 内容 | 対応 |
| --- | --- | --- |
| 1 | **固有名詞・条項番号の完全一致に弱い** | 現時点の対象文書には該当する用途が無い。用途が増えたら ADR を追加して④を再検討する |
| 2 | **横断集計・時系列の質問に答えられない** | [requirements.md](../requirements.md) 3-3 の「やらないこと」に明記して合意済み |
| 3 | **多言語の文書が混ざると精度が落ちる** | 発生したら埋め込みモデルの見直しが必要。**全件の再埋め込みになる**（ADR-002 の結果を参照） |
| 4 | 分割の設計が未確定 | `3-3-8` で質問セット20問を使って測り、決める。**測定結果は別 ADR に残す** |

**要件が変わったときの影響**

| 変化 | 影響 | 構成の変更 |
| --- | --- | --- |
| データ量10倍（350ファイル） | 取り込みの時間と費用が10倍。検索は索引が効くので耐える | **不要**（差分更新の実装は要る） |
| リアルタイム更新 | 取り込みが手動なので成立しない | **必要**（ADR を追加する） |
| 多言語 | 埋め込みモデルの見直し。全件の再埋め込み | **必要** |
