# ADR-003: ベクトルストアに Supabase（PostgreSQL＋pgvector）を使う

| 項目 | 内容 |
| --- | --- |
| 状態 | 採用 |
| 日付 | 2026-08-09 |
| 関係する要件 | [requirements.md](../requirements.md) 3-1 F-4／3-2 非機能・4-1 技術スタック |

## 決定

ベクトルと本文の断片を **Supabase の PostgreSQL（pgvector 拡張）** に保存する。近傍検索は SQL から実行する。

## 背景

- ADR-001 でベクトル検索を採用し、ベクトルの保存先が必要になった
- 対象は約35ファイル・分割後で数千件の断片を想定。**この規模では、どの選択肢でも性能は足りる**
- 運用者が文書を取り込み直す運用（要件 F-4）があり、**重複の防止と削除が必要**
- 将来、取り込みの履歴や利用状況を残す可能性がある
- **このとき分かっていなかったこと**：断片の件数が最終的にどのくらいになるか。分割の設計が未確定のため、**数千〜数万の幅で見ていた**

## 代替案

| 案 | 内容 |
| --- | --- |
| A | ベクトル専用のマネージドサービスを使う |
| B | ベクトルをファイルに保存し、メモリ上で検索する |

## 棄却理由

**A（ベクトル専用サービス）── 運用要件（F-4）の実装が増える**

設定が最も簡単で、この規模なら性能も十分。ただし**SQL が使えないため、重複の防止・削除・取り込み履歴の管理をすべてアプリ側で実装することになる。**「同じファイルを2回取り込んでも重複しない」（F-4 の合格条件③）を、サービスごとの API に合わせて自前で作る必要がある。

あわせて、将来ベクトル以外のデータ（取り込み履歴・利用ログ）を持つとき、**保存先がもう1つ増える。**

**この案を選ぶとしたら**：断片が数百万件を超え、専用サービスの検索性能が必要になったとき。

**B（ファイル・メモリ上）── 運用要件（非機能6）が落ちる**

費用がゼロで、この件数なら検索も十分速い。しかし**Vercel Functions は実行のたびに状態が失われる**ため、索引をビルド時に作り込む形になる。文書を1件直すたびに再デプロイが必要になり、**「運用者が取り込み直せる」（非機能6）を満たさない。**

**この案を選ぶとしたら**：文書がほとんど更新されず、更新のたびにデプロイして構わないとき。

## 結果

**できるようになったこと**

- 断片の重複防止・削除を **SQL の制約と `DELETE` で実装できる**（F-4 の合格条件③）
- 取り込み履歴や利用状況を、同じデータベースに置ける
- **クエリの実行計画を見られる**ため、遅くなったときに原因を追える（`3-3-10`）
- 無料枠の範囲で運用を始められる

**できなくなったこと・引き受けたリスク**

| # | 内容 | 対応 |
| --- | --- | --- |
| 1 | **接続情報の管理が増える**（3つ目の外部サービス） | ADR-002 と同じく、サーバー側の環境変数で管理する |
| 2 | 断片が数百万件を超えると、索引の調整が必要 | **現時点の想定は数千件。**桁が2つ上がったら A を再検討する |
| 3 | 無料枠の上限（容量・行数・帯域）に達する可能性 | `3-3-11` の費用見積もりで、想定利用量に対する余裕を確認する |
| 4 | 保存地域とデータの扱いを、クライアントに説明する必要がある | [notes/external-services.md](../notes/external-services.md) 3章で確認して提出する |

**測っていないこと**

近傍検索の索引（インデックス）をどう張るかは、**断片の件数が確定してから決める。**現時点では索引なしでも数千件なら十分速いと見込んでいるが、**確認していない。**`3-3-10` で実測する。
