# 仕様書 ── 社内文書検索アシスタント v1.1

> **この文書は判断基準だけを置く。**合否はここに書いてあることだけで決める。
> 背景・利用者・やらないことは [requirements.md](./requirements.md)、根拠や測定の記録は [notes/](./notes/) にある（`2-2-5`）。
>
> **受け入れ基準はこの文書にしか書かない。**他の文書からは参照するだけにする（`2-3-6`）。

| 項目 | 内容 |
| --- | --- |
| 版 | v1.1 |
| 最終更新 | 2026-08-27 |

---

## 1. 目的

社内のルールに関する質問に、対象文書を根拠として答える。

---

## 2. 入力

### 2-1 質問（利用者）

| 項目 | 内容 |
| --- | --- |
| 形式 | プレーンテキスト（1行） |
| 上限 | **200 文字** |
| 下限 | **5 文字** |
| 必須 | 空文字・空白のみは受け付けない |

> 上限・下限の根拠と測定は [notes/query-limit.md](./notes/query-limit.md) にある。

### 2-2 対象文書（運用者）

| 項目 | 内容 |
| --- | --- |
| 形式 | `.md` / `.txt` / `.pdf`（テキストが埋まっているもの） |
| 1ファイルの上限 | **100,000 文字** |
| 件数の上限 | **50 ファイル** |
| 文字コード | UTF-8 |

---

## 3. 出力

### 3-1 回答が作れた場合

| 項目 | 形式 |
| --- | --- |
| `answer` | 文字列。**600 文字以内** |
| `sources` | 配列。1件以上3件以下 |
| `sources[].document` | 文字列。対象文書のファイル名 |
| `sources[].excerpt` | 文字列。根拠となった箇所。**200 文字以内** |

### 3-2 回答が作れない場合

| 項目 | 形式 |
| --- | --- |
| `answer` | `null` |
| `sources` | 空配列 |
| `reason` | `"no_match"`（根拠が見つからない）／ `"low_confidence"`（見つかったが根拠として弱い） |

**`answer` が `null` のとき、画面には「対象の文書に記載が見つかりませんでした」と、次にどうするか（Slack で総務部に聞く）を表示する。**

### 3-3 失敗した場合

| 項目 | 形式 |
| --- | --- |
| `failureKind` | `empty_input` / `too_long` / `too_short` / `timeout` / `rate_limited` / `quota_exceeded` / `embedding_error` / `db_error` / `api_error` |

---

## 4. 受け入れ基準

> **各基準は「正常系・合格条件・異常系」の3部品で書く**（`2-2-4`）。1つでも欠けるとそこがすり抜ける。

### F-1 質問を送信できる

| 部品 | 内容 |
| --- | --- |
| 正常系 | 質問を入力して［質問する］を押すと、処理が始まる |
| 合格条件 | 処理中であることが画面に表示され、**ボタンが二重に押せない** |
| 異常系 | 空・空白のみ・5文字未満・200文字超のときは**送信せず**、どの条件に当たったかを表示する |

**判定方法：**空文字・空白4文字・201文字の3件を送り、いずれも外部 API が呼ばれないことをログで確認する。

---

### F-2 根拠つきの回答が返る

| 部品 | 内容 |
| --- | --- |
| 正常系 | 対象文書に記載のある質問を送ると、回答と根拠が返る |
| 合格条件 | ① `answer` が600文字以内　② `sources` が1件以上3件以下　③ 各 `sources[].document` が**実在する対象文書のファイル名**である　④ 各 `sources[].excerpt` が**その文書に実際に含まれる文字列**である |
| 異常系 | 3章3-3のいずれかに分類され、画面が操作可能なまま理由が表示される |

> 📌 **③④は機械で判定できます。**
> 「回答が正しいか」は判定できませんが、**「示した根拠が実在するか」は判定できます。**これが LLM を使う機能の受け入れ基準の立て方です（Constitution 第13条1・`2-2-4`）。

**判定方法：**`sources[].document` を対象文書の一覧と突き合わせる。`sources[].excerpt` を該当文書の本文に対して部分一致で検索する。

---

### F-3 根拠が無いときは答えを作らない

| 部品 | 内容 |
| --- | --- |
| 正常系 | 対象文書に記載の無い質問を送ると、`answer` が `null` で返る |
| 合格条件 | ① `answer` が `null`　② `sources` が空配列　③ `reason` が `"no_match"` または `"low_confidence"`　④ 画面に「記載が見つかりませんでした」と次の行動が表示される |
| 異常系 | ── |

**判定方法：**[notes/eval-set.md](./notes/eval-set.md) の「対象外」5問を送り、5問すべてで `answer` が `null` になること。

> ⚠️ **この基準がこの案件の合否を分けます。**
> クライアントの条件は「間違ったことを自信満々に答えられるのがいちばん困る」でした。**1問でも作話したら不合格**として扱う。

---

### F-4 文書を取り込める

| 部品 | 内容 |
| --- | --- |
| 正常系 | 運用者が対象文書を置いて取り込みを実行すると、検索対象に反映される |
| 合格条件 | ① 取り込んだ件数・スキップした件数・失敗した件数が表示される　② 失敗したファイルは**ファイル名と理由**が分かる　③ 同じファイルを2回取り込んでも**重複して登録されない** |
| 異常系 | 上限超過・非対応形式・テキストが取り出せない PDF は**スキップし、理由を出す**。他のファイルの処理は続行する |

**判定方法：**①② は、正常なファイル・上限超過ファイル・非対応形式・テキストが取り出せない PDF を混ぜた一式で取り込みを実行し、件数と理由の表示を確認する。③ は、同じファイルで取り込みを2回実行し、検索対象の登録件数が増えないことを確認する（`scripts/ingest.ts`）。

> 📌 **③の重複防止を基準に入れているのは、運用で必ず起きるからです。**
> 文書を1件直したときに全件を取り込み直すのが自然な運用になります。**重複すると、同じ根拠が3件並んで `sources` が埋まります。**

---

### F-5 失敗しても画面が壊れない

| 部品 | 内容 |
| --- | --- |
| 正常系 | ── |
| 合格条件 | 3章3-3の**すべての `failureKind`** について、① 画面が操作可能なまま　② 何が起きたかが表示される　③ 次にどうするかが表示される |
| 異常系 | ── |

**判定方法：**外部サービスのクライアントをモックに差し替え、各 `failureKind` を発生させるテストを書く（`2-4-13` と同じ形）。

> 📌 **`quota_exceeded`（上限到達）を必ず含めること。**
> 費用の上限を設定する以上、**到達したときの挙動は仕様の一部**です（[requirements.md](./requirements.md) 3-2）。

---

### F-6 動作が記録される

| 部品 | 内容 |
| --- | --- |
| 正常系 | 1リクエストにつき1行、構造化ログが出る |
| 合格条件 | ① `requestId` / `queryChars` / `hitCount` / `topScore` / `answered`（真偽）/ `failureKind` / `latencyMs` / `inputTokens` / `outputTokens` が記録される　② **質問文・回答本文・根拠の抜粋・API キーが記録されない** |
| 異常系 | ── |

**判定方法：**ログの型に**質問文と回答本文を入れる欄を作らない**（`2-4-13`）。書こうとすると型で落ちる形にする。

> 📌 **②はクライアントの条件です。**
> 「送った内容をログに残さない」（[hearing.md](./hearing.md) Q9 条件3）。**ログから中身が読めると、外部送信の合意条件を破ることになります。**

## 5. 非機能の基準

| # | 観点 | 基準 | 判定方法 |
| --- | --- | --- | --- |
| 1 | **応答時間** | 質問の送信から回答表示まで、**中央値で20秒以内**。**30秒で打ち切る** | [notes/eval-set.md](./notes/eval-set.md) の20問を実行して測る |
| 2 | **打ち切り** | 30秒を超えたら `timeout` として扱い、リトライは**最大2回**まで | テストで確認 |
| 3 | **費用** | 1回の質問あたり**3円以内**。月間の上限を各サービスに設定する | [notes/cost-estimate.md](./notes/cost-estimate.md) |
| 4 | **取り込み** | 50ファイルの取り込みが**10分以内**に終わる | 実測 |

> **応答時間の中央値20秒は、現状の「自分で探す6分」に対する目標です。**
> 平均ではなく中央値で見るのは、外部サービスの遅延で平均が引っ張られるためです。

> 📌 **[requirements.md](./requirements.md) 3-2 の性能欄「10秒以内（目安）」との関係。**
> 10秒はヒアリング時点の目安であり、合否には使わない。**合否の判定は本表（中央値20秒・30秒打ち切り）だけで行う**（受け入れ基準は本仕様書にのみ置く）。埋め込みと生成の2段の外部呼び出しがあるため、どこからどこまでを測るかを含めてこの形に確定した。

## 6. やらないこと

**[requirements.md](./requirements.md) 3-3 に一覧がある。**この仕様書では繰り返さない。

**この仕様書の範囲で特に確認すること：**

| # | 内容 |
| --- | --- |
| 1 | 横断集計（「〜は何件か」）に答えられないことは**不具合ではない**。F-3 の挙動になれば合格 |
| 2 | 時系列（「いつ変わったか」）に答えられないことも同様 |
| 3 | 対象文書に無い一般知識に答えないことも同様。**答えたら F-3 の不合格** |

## 7. requirements との対応

**[requirements.md](./requirements.md) 3-1 の機能要件と、本仕様書の基準の対応。**合否は本仕様書の側で判定する。

| requirements 3-1 | 本仕様書 |
| --- | --- |
| F-1 質問入力 | F-1 |
| F-2 回答表示（根拠つき回答、または「分からない」） | F-2・F-3 |
| F-3 根拠表示（文書名と抜粋1〜3件） | F-2（合格条件②〜④） |
| F-4 文書取り込み | F-4 |
| F-5 利用上限 | F-5（`quota_exceeded` の挙動）・5章の非機能3（上限の設定） |

> 📌 **番号の付け方が両文書で異なる。**requirements は「何を作るか」の分解、本仕様書は「何で合否を決めるか」の分解であり、本仕様書の番号は教材本文の機能一覧（`3-1-0`）と揃えている。突き合わせはこの表で行う。ログ（F-6）は requirements 3-2 の非機能要件（プライバシー）に対応する。
