## 2. 実装の順番 ── インターフェースを先に、外部を最後に

```
ステップ0  ガードレールを渡す（セッションの最初の指示）
ステップ1  types.ts       ── 出力の型・失敗の分類（spec 3章）
ステップ2  validate.ts    ── 5〜200文字。送る前に止める（F-1）
ステップ3  chunk.ts       ── 文書の分割
ステップ4  clients.ts ＋ tests/fakes.ts ── 外部3サービスのインターフェース
ステップ5  prompt.ts      ── 根拠束縛。断片0件なら生成を呼ばない（F-3）
ステップ6  verify.ts      ── 根拠の実在チェック（F-2 ③④）
ステップ7  errors.ts      ── transient / permanent / malformed の分類
ステップ8  ask.ts         ── 束ねる＋統合テスト（F-1〜F-3・F-5）
ステップ9  logger.ts      ── 質問文・回答本文の欄が無いログ（F-6）
ステップ10 providers.ts ＋ env.ts ── SDK の実装と起動時チェック
ステップ11 route.ts ＋ 画面 ── サーバー側の入口と3状態の UI
ステップ12 取り込み       ── schema.sql と scripts/ingest.ts（F-4）
ステップ13 仕上げ         ── F-1〜F-6 との突き合わせ
```

### 2-1 この順番の要点は「ステップ4」です

**外部サービスの SDK を書く前に、インターフェース（`EmbeddingClient` / `VectorStore` / `MessagesClient`）と偽物（`tests/fakes.ts`）を先に作ります。**

| 先に作ると | 後回しにすると |
| --- | --- |
| ステップ5〜9 が**キー無し・0円**でテストできる | どの部品のテストにも実接続が要る |
| `tests/` から SDK を import しない構造が**最初から成立**する | あとから「テストが外部を呼んでいた」を剥がすことになる |
| 本物（providers.ts）は**最後に1回だけ**書けばよい | SDK の仕様変更のたびに全部品に波及する |

**`3-3-9` で学ぶ「インターフェース差し替え」を、設計の順番として先に使うということです。**

### 2-2 並列に振れるところ（`3-2-6`・`3-2-7`）

ステップ3・5・6・7 は互いに依存しません（すべてステップ1の型だけに依存）。**1セッションで順にやってもよいし、`3-2-7` のタスク分割で「入力が同じで出力が交わらない」ことを確認して、`3-2-6` のサブエージェント／Git Worktree に振ってもかまいません。**初回は逐次を推奨します。並列は、逐次で1周して部品の境界が頭に入ってからのほうが、失敗したときに切り分けられます。

## 3. 各ステップの指示プロンプト

プロンプトの型は minutes-app と同じです（①作るもの ②参照する仕様 ③やらないこと ④確認方法）。**ここでは Phase 3 固有の要点があるステップだけ全文を載せ、型どおりのステップは要点だけ示します。**

### ステップ0 ガードレールを渡す

```
社内文書検索アシスタント（RAG）を実装します。セッション全体のルールです。

【仕様と設計】
- docs/spec.md（F-1〜F-6）が唯一の判断基準です。書かれていないことは
  推測せず、質問として報告してください。
- 構成の選定は docs/adr/ の3本で決定済みです。構成を選び直す提案は
  しないでください。
- データベースの定義は docs/schema.sql が正です。

【構成のルール】
- SDK（@anthropic-ai/sdk・openai・@supabase/supabase-js）に触れるのは
  lib/providers.ts だけ。他の lib/ は lib/clients.ts のインターフェース
  にだけ依存させます。
- tests/ から lib/providers.ts と各 SDK を import してはいけません。
- corpus/（対象文書35件）は読み取り専用です。変更・追加しないでください。

【テストのルール】
- LLM の出力の文面を期待値にしたテストを書かないでください
  （判定してよいのは形式と、根拠の実在だけです）。
- テストは外部を呼ばず、tests/fakes.ts の偽物で完結させます。

【進め方】
- 指示した部品だけを作る。各ステップの終わりに ./scripts/verify を実行。npm コマンドをホストで直接実行しない。
まだ実装は始めないでください。不明点があれば先に質問してください。
```

**minutes-app のステップ0との差分は3つです。**①ADR で構成の再提案を封じる、②SDK に触れる場所を1ファイルに限定する、③「出力の文面を期待値にしない」（Constitution 第13条1）をテスト規約として先に渡す。

### ステップ1〜3（型・検証・分割）

型どおりです。参照先だけ示します。

| ステップ | 参照する仕様 | 確認方法 |
| --- | --- | --- |
| 1 `types.ts` | spec 3章（`AskResult`・`Source`）と失敗の分類（`transient`／`permanent`／`malformed`・`AskError` は `service` 欄で**どのサービスの失敗か**を持つ） | `./scripts/verify` の型チェック |
| 2 `validate.ts` | spec 2-1（**5〜200文字**・空と空白のみは不合格） | 境界4件（4字・5字・200字・201字）のテスト |
| 3 `chunk.ts` | 分割の方針（`3-3-8`。断片に `document` と `chunk_index` を持たせ、どの文書の何番目かを失わない） | 単体テスト |

### ステップ4 clients.ts ＋ tests/fakes.ts（このアプリの要）

```
lib/clients.ts と tests/fakes.ts を作ってください。

【作るもの】
- 外部3サービスの最小インターフェース：
  - EmbeddingClient（テキスト → ベクトル）
  - VectorStore（ベクトル → 類似断片の検索、断片の保存）
  - MessagesClient（プロンプト → 生成テキスト）
- Clients 型（3つをまとめて持ち回る）
- tests/fakes.ts：3つの偽物。呼ばれた回数を数えられるようにする
  （「呼ばれていないこと」をテストで確かめるため）

【制約】
- SDK を import しない。ここは型とインターフェースだけのファイルです。
- インターフェースには、このアプリが使う操作だけを載せる。SDK の
  機能を写さない。

【確認】
- fakes が3つともインターフェースを満たして型チェックが通ること。
```

> 📌 **「呼ばれた回数を数えられる偽物」が、費用の受け入れ基準を支えます。**
> spec F-1 の判定方法は「短すぎる質問で**外部 API が呼ばれない**ことを確認する」です。回数を数えられない偽物だと、この基準がテストにできません。

### ステップ5 prompt.ts（根拠束縛・F-3）

```
lib/prompt.ts と tests/unit/prompt.test.ts を作ってください。

【作るもの】
- 検索で得た断片と質問からプロンプトを組み立てる関数
- enforceGrounding：断片が0件のとき、生成を呼ばずに「答えられない」
  へ分岐させるための判定
- プロンプトの制約：断片に書かれていないことを答えない・答えられない
  ときは決められた形で返す

【参照する仕様】
- spec F-3（根拠が無いときは答えを作らない）と 3-2（answer: null / reason）

【確認】
- 断片0件で生成が呼ばれない分岐がテストできること（実際の検証は
  ステップ8の統合テストで、fakes の呼び出し回数0として確かめます）。
```

> ⚠️ **F-3 はこの案件の合否を分ける基準です**（spec F-3 の注記）。
> 「作話したら不合格」を守る実装は、生成モデルへのお願い（プロンプト）だけでは足りません。**断片0件なら生成を呼ばない**という構造（呼ばなければ作話できない）で守ります。

### ステップ6 verify.ts（根拠の実在・F-2 ③④）

```
lib/verify.ts と tests/unit/verify.test.ts を作ってください。

【作るもの】
- 生成結果の sources を検証する関数：
  - sources[].document が、検索で渡した断片の文書名に実在するか
  - sources[].excerpt が、その文書の本文に部分一致で実在するか
- 実在しない根拠が混ざっていたら不合格として扱う

【参照する仕様】
- spec F-2 合格条件③④と、その判定方法

【確認】
- テストに必ず入れる：実在する根拠（合格）／実在しない文書名（不合格）
  ／文書名は実在するが excerpt が本文に無い＝要約されている（不合格）。
```

> 📌 **「回答が正しいか」は判定できませんが、「示した根拠が実在するか」は判定できます**（spec F-2 の注記）。
> LLM を使う機能の受け入れ基準の立て方そのものです。3つ目のテストケース（**要約された抜粋は不合格**）が抜けやすいので、指示に明記しています。

### ステップ7 errors.ts（失敗の分類）

型どおりです。分類は2軸で持たせます。

| 軸 | 値 | 用途 |
| --- | --- | --- |
| **再試行の分類**（`FailureKind`） | `transient`（429・5xx・ネットワーク層＝再試行してよい）／`permanent`（4xx・不明＝再試行しても同じ）／`malformed`（形式の崩れ＝**1回だけ**再試行） | `classify(status, cause)` で HTTP ステータスから機械的に決める |
| **利用者向けの識別子**（`code`） | `INVALID_INPUT`／`EMBEDDING_FAILED`／`SEARCH_FAILED`／`GENERATION_FAILED`／`MALFORMED_RESPONSE`／`INTERNAL` | 画面の文言とログを引き当てる。**文言に内部情報（接続文字列・キー・スタック）を混ぜない**（spec 3-3・F-5） |

あわせて `service` 欄（embedding／vectorStore／generation／app）で**どのサービスで失敗したか**を持ちます。`3-1-3` で呼び先が3つに増えた分、切り分けの材料を分類の時点で残す設計です。「分からないものは `permanent` に倒す」（無限に再試行させない）も指示に含めてください。

### ステップ8 ask.ts ＋ 統合テスト

```
lib/ask.ts と tests/integration/ask.test.ts を作ってください。

【作るもの】
- ask(input, deps)：validate → 埋め込み → 検索 → （断片0件なら生成を
  呼ばず「答えられない」）→ 生成 → verify → 整形、を束ねる関数。
  deps は Clients（ステップ4）で受け取る。
- malformed のときだけ1回再試行。verify 不合格も malformed として扱う。

【確認（統合テスト・すべて fakes で）】
- 4文字の質問 → 不合格が返り、3つの偽物の呼び出し回数がすべて0
- 正常な質問 → answer と sources（1〜3件）が返る
- 検索0件 → answer が null、reason が入り、生成の呼び出し回数が0
- 生成が実在しない根拠を返す → 再試行1回ののち失敗として分類される
- 検索が 500 を返す → transient に分類され、画面向けメッセージが返る
```

### ステップ9〜11（ログ・SDK 実装・入口と画面）

| ステップ | 要点 |
| --- | --- |
| 9 `logger.ts` | `AskLog` に**質問文・回答本文・抜粋の欄を作らない**（spec F-6。書こうとすると型で落ちる）。記録するのは `requestId`・文字数・件数・スコア・所要時間・トークン数・`failureKind` |
| 10 `providers.ts`＋`env.ts` | SDK の実装は**ここに集約**。`env.ts` の `assertEnv` が起動時に4変数の欠落を止める（`3-3-11`。無いまま動かすと、質問したときに初めて失敗する）。**このファイルはテスト対象外**であることを明示する |
| 11 `route.ts`＋`app/page.tsx` | 入口で `assertEnv` → `ask` を呼ぶ。画面は質問欄・回答・**根拠（文書名と抜粋）**・答えられないときの案内（spec 3-2 の文言と次の行動）・ローディング／エラーの3状態 |

### ステップ12 取り込み（F-4）── 実装の外に1つだけ手作業があります

```
scripts/ingest.ts を作ってください。

【作るもの】
- corpus/ の .md / .txt を読み、chunk → 埋め込み → Supabase へ保存
- 実行結果として、処理件数・失敗件数・未対応の形式（PDF）の件数を
  表示する（spec F-4：失敗したファイルは名前と理由が分かること）
- 同じファイルを2回取り込んでも重複しないこと（spec F-4 ③）

【前提（人が先にやること）】
- Supabase のプロジェクトで docs/schema.sql を SQL エディタから
  1回実行しておく（テーブルと近傍検索の定義）
```

> ⚠️ **`./scripts/ingest`（コンテナ内の `npm run ingest`）は外部 API を呼び、費用が出ます**（埋め込み。見積もりは [notes/cost-estimate.md](../notes/cost-estimate.md)）。
> `./scripts/verify` と違って、**気軽に何度も回すコマンドではありません。**エージェントに自動実行させず、人が実行します（→ [implementation.md](./implementation.md) §3-3 ではパーミッションの `ask` に入れます）。

### ステップ13 仕上げ ── F-1〜F-6 との突き合わせ

minutes-app と同じく、エージェントに対応表を出させたうえで、**spec.md を上から読みながら自分の目で埋め直します**（Constitution 第14条1）。この完成形サンプルでは次のとおりです。

| 基準 | 実装 | テスト |
| --- | --- | --- |
| F-1 質問を送信できる | `lib/validate.ts`・画面 | `tests/unit/validate.test.ts`・統合（呼び出し回数0） |
| F-2 根拠つきの回答が返る | `lib/ask.ts`・`lib/verify.ts` | `tests/unit/verify.test.ts`・統合 |
| F-3 根拠が無いときは答えを作らない | `lib/prompt.ts`（`enforceGrounding`）・`lib/ask.ts` | `tests/unit/prompt.test.ts`・統合（生成の呼び出し0） |
| F-4 文書を取り込める | `scripts/ingest.ts`・`docs/schema.sql` | **手動確認**（件数表示・2回実行で重複しない） |
| F-5 失敗しても画面が壊れない | `lib/errors.ts`・`route.ts`・画面 | `tests/unit/errors.test.ts`・統合 |
| F-6 動作が記録される | `lib/logger.ts` | **型で守る**（本文の欄が無い） |

> ⚠️ **テスト48件が緑でも、実接続の確認は別です**（Constitution 第13条8）。
> このサンプル自体、外部サービスへの実接続とコンテナ起動は**未実施**と README に明記してあります。**何を確かめて何を確かめていないかを分けて書く**のが、`3-3-9` で学んだ守り方です。非機能の基準（中央値20秒・[notes/eval-set.md](../notes/eval-set.md) の20問）は、実接続してから測ります。

## 4. キーの設定と起動確認

### 4-1 必要な環境変数（4つ・すべて必須）

| 変数名 | 用途 | 取得先 |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | 回答の生成 | Anthropic Console（`2-4-10`） |
| `OPENAI_API_KEY` | 文書と質問の埋め込み | OpenAI Platform（`3-1-0` 2-3。**上限設定を先に**） |
| `SUPABASE_URL` | ベクトル検索の接続先 | Supabase ダッシュボード → プロジェクトの設定 → API |
| `SUPABASE_SERVICE_ROLE_KEY` | 同・サーバー側キー | 同上。**サーバー側専用。ブラウザに出さない** |

欠けたまま起動すると、`lib/env.ts` の `assertEnv` が**起動時に**「何が無いか」を出して止めます（値は出しません）。何をどこへ送るかは [notes/external-services.md](../notes/external-services.md) のとおりです。

### 4-2 設定手順

1. `cp .env.example .env.local` で作り、4つの値を書く（`.env.local` はリポジトリに入れない）
2. `git check-ignore -v .env.local` で除外を確認する（何も出なければ危険。`2-4-11`）
3. **Supabase 側の準備**：プロジェクトを作り、[docs/schema.sql](../schema.sql) を SQL エディタから**1回だけ**実行する
4. **取り込み**：`./scripts/ingest`（中身は `docker compose run --rm app npm run ingest -- corpus`。費用が出ます。実行前に [notes/cost-estimate.md](../notes/cost-estimate.md) を確認）

### 4-3 起動確認 ── 既定は Docker

**このサンプルもホストに Node.js・`node_modules` を入れない方針です。**ホストで `npm run dev` を打つと `next: command not found` 等で失敗しますが、**異常ではなく既定の状態です。**

```bash
docker compose build     # 初回のみ
./scripts/dev            # コンテナ内で開発サーバーが起動する（中身は docker compose up）
```

1. **ブラウザで http://localhost:3000 を開く**
2. 対象文書に記載のある質問（例は [notes/eval-set.md](../notes/eval-set.md) の Q1）を送り、**回答と根拠（文書名・抜粋）**が返ることを確かめる
3. 対象外の質問（同・対象外5問）を送り、**「記載が見つかりませんでした」**になることを確かめる（F-3）
4. 4文字の質問を送り、**送信前に止まる**ことを確かめる（F-1）
5. 終了は Ctrl+C、片付けは `docker compose down`。判定器は `./scripts/verify`

**ホストで `npm run dev` したい場合（非推奨・旧手順）**：minutes-app と同じ手順です（Node.js 22 系を用意 → `npm install` → `npm run dev`。方針から外れることを理解したうえで。[minutes-app の手順書 4-4](../../../minutes-app/docs/procedure/README.md) 参照）。

### 4-4 Vercel への登録（公開まで進める場合）

`3-3-11` の手順どおりです。**4変数すべて**を Settings → Environment Variables に登録 → Production 適用を確認 → **登録後に再デプロイ** → 公開 URL で1回動かして確認 → 公開ページの JavaScript にキー文字列が無いことを検索で確認。`ingest` は公開後もローカルから実行する運用です（取り込み API を公開しない構成）。
