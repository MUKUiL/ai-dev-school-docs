## 1. 何が「一気に」を可能にするのか

原理は minutes-app と同じです。**セッション中に人がやっていた判断を、ファイルに置き換えます。**Phase 3 では、置き換えるべき判断が増えています。

| セッション中に人がやっていたこと | 置き換わるファイル | 対応する節 |
| --- | --- | --- |
| 部品の順番の指示 | `PLANS.md` | `2-3-6`・`2-3-7`・`3-2-7` |
| 合否の基準の参照 | `docs/spec.md`（F-1〜F-6） | `3-1-2` |
| **構成の選定**（検索方式・プロバイダ・保存先） | **`docs/adr/` の3本** | `3-1-4` |
| **データベース定義の判断** | **`docs/schema.sql`** | `3-3-8` |
| ルールの都度注意 | `CLAUDE.md` | `2-5-15` |
| 危険・**高額**な操作の目視確認 | `.claude/settings.json` | `2-5-15`・`3-3-11` |
| 「テストを回して」 | `./scripts/verify`（判定器の入口。コンテナ内で型チェック＋テスト） | `2-1-2`・`3-3-9` |

**Phase 2 との最大の違いは、太字の2行です。**外部サービスが3つある構成では、エージェントは実装のたびに「Supabase より Pinecone が…」のような**構成の選び直し**を始めがちです。ADR がリポジトリにあると、「決定済み。理由はここ」で判断が固定されます。**設計文書は、一気通貫では『エージェントを迷わせないための壁』として働きます。**

## 2. リポジトリに置くファイル一式

```
docsearch-app/
├── CLAUDE.md                 ← ガードレール … §3-2
├── PLANS.md                  ← 実行計画 … §5
├── .claude/settings.json     ← パーミッション … §3-3
├── .gitignore                ← .env を必ず含める
├── .env.example              ← 環境変数のテンプレート（4変数・値は書かない）… §8
├── package.json              ← "verify" と "ingest" … §4
├── docs/
│   ├── requirements.md / spec.md      ← 何を作るか／何で合否を決めるか（確定済み）
│   ├── adr/（3本）                     ← 構成の決定と理由（確定済み）
│   ├── schema.sql                     ← Supabase 側の定義（確定済み）
│   └── notes/（query-limit・cost-estimate・eval-set・external-services）
├── corpus/                   ← 対象文書35件（読み取り専用）
├── lib/ , app/ , scripts/    ← これから作られる
└── tests/                    ← これから作られる
```

**実装が空でも、仕様・設計・計画・ルール・判定器の5つが先にそろっている**のは minutes-app と同じです。違いは、**設計（ADR・schema.sql）までがその中に入る**ことです。

## 3. ガードレールの設定方法

3層の考え方（`2-1-1`）は minutes-app と同じです。ここではこのアプリ固有の割り当てだけ示します。

| このアプリ固有の事故 | 層 | 置き場所 |
| --- | --- | --- |
| **費用の出るコマンド（`./scripts/ingest`）を自動で回される** | ① | `settings.json` の `ask` |
| 構成を選び直される（別のベクトル DB の提案など） | ① | `CLAUDE.md`（ADR 参照の宣言） |
| `corpus/`（対象文書）を書き換えられる | ① | `CLAUDE.md`＋差分レビュー |
| テストが SDK を直接呼ぶ構造になる | ①③ | `CLAUDE.md`＋import の検査 |
| LLM 出力の文面がテストの期待値に入る | ② | `CLAUDE.md`＋終了後レビュー（第13条1） |

### 3-2 CLAUDE.md の内容（このアプリ版・minutes-app との差分）

共通部分（変更の範囲・テストを緩めない・停止条件など）は [minutes-app 版](../../../minutes-app/docs/procedure/implementation.md) と同じです。**このアプリで追記するのは次のブロックです。**

```markdown
## 設計の固定

- 構成（検索方式・プロバイダ・ベクトルストア）は docs/adr/ で決定済み。
  別の構成の提案・変更をしない。
- docs/schema.sql が DB 定義の正。実装側の都合で変えない。変更が必要に
  なったら止めて報告する。

## 構成のルール

- SDK（@anthropic-ai/sdk・openai・@supabase/supabase-js）に触れるのは
  lib/providers.ts だけ。他の lib/ は lib/clients.ts のインターフェース
  にだけ依存させる。
- tests/ から lib/providers.ts と各 SDK を import しない。
- corpus/ は読み取り専用。変更・追加・削除をしない。

## テストのルール

- LLM の出力の文面を期待値にしたテストを書かない。判定してよいのは
  形式と、根拠の実在（verify）だけ。
- テストは tests/fakes.ts の偽物で完結させ、外部を呼ばない。

## 費用の出る操作

- 取り込み（./scripts/ingest）は実行しない（人が実行する）。実行が必要だと
  判断したら、止めて報告する。
```

### 3-3 .claude/settings.json（このアプリ版）

minutes-app 版との違いは1行だけですが、その1行が Phase 3 の学びどころです。

```json
{
  "permissions": {
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(rm *)"
    ],
    "ask": [
      "Bash(./scripts/install)",
      "Bash(./scripts/ingest)",
      "Bash(docker compose build *)",
      "Bash(docker compose run --rm app *)",
      "Bash(vercel *)",
      "Bash(git push *)"
    ],
    "allow": [
      "Bash(./scripts/verify)",
      "Bash(npm test)",
      "Bash(./scripts/dev)",
      "Bash(docker compose up *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ]
  }
}
```

> ⚠️ **`ask: Bash(./scripts/ingest)` が追加行です。**
> `verify` は fakes で回るので**0円・allow**、`ingest` は埋め込み API を呼ぶので**費用が出る・ask**。**「機械に何度でも回させるもの」と「回すたびにお金が出るもの」を、パーミッションの段階で分ける**ということです（費用の見積もりは [notes/cost-estimate.md](../notes/cost-estimate.md)）。

## 4. 判定器 ── verify は 0 円、ingest は費用が出る

| コマンド | 中身 | 外部呼び出し | 扱い |
| --- | --- | --- | --- |
| `./scripts/verify` | コンテナ内で `tsc --noEmit && vitest run`（48件） | **無し**（fakes で完結） | ループの判定器。何度でも回す |
| `./scripts/ingest` | corpus の埋め込みと保存（コンテナ内で `npm run ingest -- corpus`） | **有り**（OpenAI・Supabase） | 人が実行（§8-3） |

**判定器が 0 円で回るのは、インターフェース先行の設計（[README.md](./README.md) ステップ4）の結果です。**逆に言うと、テストのどこかが SDK を import した瞬間、この前提は崩れます。CLAUDE.md の「テストのルール」と、検収時の import 検査（§9）で守ります。

## 8. 環境変数の設定と起動確認

**実装とテストのループは4つのキーが1つも無くても最後まで走ります**（判定器は fakes で完結・§4）。キーが要るのは、人の作業である**取り込み・手動確認・公開**です。

### 8-1 必要な環境変数（4つ・すべて必須）

| 変数名 | 用途 | 取得先 |
| --- | --- | --- |
| `ANTHROPIC_API_KEY` | 回答の生成 | Anthropic Console（`2-4-10`） |
| `OPENAI_API_KEY` | 文書と質問の埋め込み | OpenAI Platform（`3-1-0` 2-3。**先に使用上限を設定**） |
| `SUPABASE_URL` | ベクトル検索の接続先 | Supabase ダッシュボード → プロジェクトの設定 → API |
| `SUPABASE_SERVICE_ROLE_KEY` | 同・サーバー側キー | 同上。**ブラウザに出さない** |

欠けたまま起動すると `lib/env.ts` の `assertEnv` が**起動時に**止めます（「何が無いか」だけを出し、値は出さない・`3-3-11`）。**キーの設定はエージェントに任せず人がやります**（`deny` により `.env.local` は読めませんし、指示するとキーが会話ログに残ります）。

### 8-2 `.env.local` の作成

```bash
cp .env.example .env.local     # テンプレートから作り、4つの値を書く
git check-ignore -v .env.local # 除外の確認。何も出なければ危険（2-4-11）
```

### 8-3 取り込み（人が実行・費用が出ます）

1. Supabase のプロジェクトで [docs/schema.sql](../schema.sql) を SQL エディタから**1回だけ**実行する
2. 費用の見込みを [notes/cost-estimate.md](../notes/cost-estimate.md) で確認する
3. `./scripts/ingest` を実行し、**処理件数・失敗件数・未対応（PDF）の件数**の表示を確認する（spec F-4）
4. もう一度実行し、**重複して登録されない**ことを確認する（spec F-4 ③）

### 8-4 起動確認 ── 既定は Docker

ホストに Node.js・`node_modules` を入れない方針のため、**ホストで `npm run dev` を打つと `next: command not found` 等で失敗します。異常ではなく既定の状態です。**

```bash
docker compose build     # 初回のみ
docker compose up        # コンテナ内で npm run dev が起動する
```

1. **ブラウザで http://localhost:3000 を開く**
2. 対象文書にある質問（[notes/eval-set.md](../notes/eval-set.md) の Q1）→ **回答と根拠**が返る
3. 対象外の質問（同・対象外5問）→ **「記載が見つかりませんでした」**になる（F-3）
4. 4文字の質問 → **送信前に止まる**（F-1）
5. 終了は Ctrl+C、片付けは `docker compose down`

**ホストで `npm run dev` したい場合（非推奨・旧手順）**：Node.js 22 系を用意 → `npm install` → `npm run dev`（ホストに `node_modules` が入る。方針から外れることを理解のうえで。手順の詳細は [minutes-app 版 §8-3](../../../minutes-app/docs/procedure/implementation.md)）。

### 8-5 Vercel への登録（公開まで進める場合）

`3-3-11` のとおり。**4変数すべて**を Settings → Environment Variables へ登録 → Production 適用を確認 → **登録後に再デプロイ** → 公開 URL で1回動かす → 公開ページの JavaScript にキー文字列が無いことを検索で確認。`ingest` は公開後もローカルから人が実行します（取り込みの入口を公開しない構成）。

## 9. 終わった後、人がやること ── 検収

minutes-app の検収（差分・依存・テスト改変・突き合わせ・手動確認）に、このアプリ固有の3つを足します。

| 順 | やること | なぜ |
| --- | --- | --- |
| 1 | `git diff --stat` に **corpus/ と docs/ の変更が無い**ことを見る | 対象文書と設計文書は読み取り専用 |
| 2 | `tests/` の import に **providers.ts・SDK が無い**ことを検索する | 判定器0円の前提（R2） |
| 3 | テストの期待値に **LLM の出力の文面が無い**ことを見る | Constitution 第13条1 |
| 4 | T13 の表を、spec.md を上から読みながら自分の目で埋め直す | 第14条1 |
| 5 | §8 の手順で取り込み〜手動確認を行う | **verify の緑は実接続の確認ではない**（第13条8） |

> ⚠️ **非機能の基準（中央値20秒・1問3円以内）は、実接続後に [notes/eval-set.md](../notes/eval-set.md) の20問で測って初めて判定できます。**
> 実装セッションの完了報告に「非機能も合格」と書かれていたら、それは**測っていない合格**です。

| 計画 | 逐次 | ＋ **並列可の宣言**（T4〜T7・`3-2-7`） |
| 検収 | 差分・突き合わせ・手動確認 | ＋ **import 検査・実接続と非機能は別枠** |

**アプリが大きくなっても、増えたのは「事前にファイルへ固定する判断の種類」だけで、型は同じです。**この型は Phase 5 の模擬案件でそのまま使います。
