# 敵役レビュアー用プロンプト（`3-1-3` 配布物）

> **受講生に配るファイルです。**アーキテクチャの選定案に、わざと反論させるためのものです。
>
> ⚠️ **AI の指摘をそのまま比較表に書き足さないでください。**
> **反論は材料です。**採否を決めるのはあなたです（Constitution 第14条3）。

---

## 使い方

1. 新しいセッションを開く
2. 下の「貼り付ける内容」を貼る
3. **自分が作った比較表と選定結果を、そのまま貼る**
4. 出てきた反論を**1件ずつ**、次の3つのどれかで処理する

| 型 | どういうときに使うか |
| --- | --- |
| **退ける** | 要件に照らして問題にならない。**なぜ問題にならないかを書く** |
| **設計を直す** | 見落としていた。**どこを直すかを書く** |
| **記録する** | いま解けない。**リスクとして ADR に残す** |

> ⚠️ **「記録する」を「解決した」にしないでください。**
> `1-2-8` の「緑＝完了ではない」と同じです。**答えられない反論を、答えられないまま残せることのほうが価値があります。**

---

## 貼り付ける内容

```
あなたは、この設計案をレビューする立場の技術者です。
**設計者の味方ではありません。**この案が失敗する筋を探すのが役割です。

【あなたの役割】
- 提示された選定案に対して、反論・懸念・見落としを指摘する
- 「良いと思います」「妥当です」といった同意は書かない
- 褒めない。改善点だけを出す

【指摘の観点】（それぞれ最低1件は出すこと）
1. 要件との不一致：選定案が満たせていない要件は無いか
2. 前提の疑い：比較表の評価は、何を前提にしているか。その前提は確かか
3. 規模の変化：データ量・利用者数・質問数が増えたとき、最初に壊れるのはどこか
4. 運用：作ったあと、誰がどうやって保守するのか。手順が抜けていないか
5. 失敗時：外部サービスが落ちたとき、利用者には何が見えるのか
6. 費用：見積もりに入っていない費用は無いか

【指摘の書き方】
- 1件ずつ、次の形で書く
  - 指摘：（何が問題か）
  - 根拠：（なぜそう言えるか）
  - 起きること：（放置するとどうなるか）
- 抽象的な指摘（「スケーラビリティに懸念がある」等）は禁止。
  **どの数値がいくつになったら、何が起きるか**まで書く

【やってはいけないこと】
- 設計を作り直して提案しない。指摘までにとどめる
- 「代わりにこうすべき」と結論を出さない
- 指摘が思いつかないときに、無理に褒めない。「この観点では指摘なし」と書く
```

---

## 運営向けメモ（受講生には配らない）

| 項目 | 意図 |
| --- | --- |
| 「褒めない」を明記している | AI は既定では同意しがち。**同意を得るためのレビューにさせない** |
| 観点を6つ固定している | 思いつきの指摘ではなく、**漏れなく当てる**ため。P4・P5 でも同じ観点が使える |
| 「抽象的な指摘は禁止」 | 「スケーラビリティに懸念」では受講生が答えられない。**数値まで書かせると、答えるか記録するかを判断できる** |
| 「作り直して提案しない」 | 設計を AI に決めさせないため（第14条3）。**指摘までが AI の仕事** |
| 「指摘なしと書いてよい」 | 無理に指摘を作らせると、受講生が退けるだけの作業になる |

**この案件で出やすい指摘（想定）：**

| 観点 | 出やすい指摘 | 期待する処理 |
| --- | --- | --- |
| 1 要件 | F-4（取り込み）の重複防止が設計に無い | **設計を直す** |
| 2 前提 | 「文書35件」は現時点の値で、増える前提が無い | 退ける（要件で50件上限を合意済み） |
| 3 規模 | 質問が1日25回→250回になったら費用が10倍 | 記録する（上限設定で止まることを確認） |
| 4 運用 | 文書を削除したときにベクトルが残る | **設計を直す** |
| 5 失敗時 | 埋め込み API だけ落ちたときの挙動が未定義 | **設計を直す**（`3-3-8` で実装） |
| 6 費用 | 取り込みのやり直しの費用が見積もりに無い | 記録する |
