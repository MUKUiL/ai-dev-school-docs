## いつ使うか（トリガー）

- 新しい機能の受け入れ基準が決まった直後
- 既存の機能にテストを足すとき

## 前提

- 受け入れ基準または観点表があること（このリポジトリでは docs/spec.md の F-1〜F-5）
- テストのフレームワークと置き場所が決まっていること（CLAUDE.md を参照。このリポジトリでは Vitest・`tests/`）

## 手順

1. 受け入れ基準ごとに、観点を3列で洗い出す
   - 正常系／異常系／境界値
2. 各観点について、テストが書けるか書けないかを判定する
3. 書けるものはテストコードにする
   - 期待値は**受け入れ基準から**決める（実装を読んで決めない）
   - `it` の説明は日本語で、期待する振る舞いを1文で書く
   - 外部 API は呼ばず、モックで完結させる（CLAUDE.md の検証ループ）
4. **書けないものは、手で確かめる手順として書き出す**
   - 何を入力して、どこを見るか

## 出力形式

1. テストコード
2. 観点表（✅ 書けた／❌ 書けなかった の印つき）
3. 「❌ の観点をどう確かめるか」の手順一覧

## やらないこと

- 実装を読んで期待値を決めない
- テスト対象そのものをモックしない
- 「テストが全部通れば完了」と書かない
