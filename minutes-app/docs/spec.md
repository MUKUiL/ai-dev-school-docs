## 1. 目的

貼り付けた議事録テキストから、**決定事項**と**アクション項目**を抽出して表示する。

---

## 2. 入力

| 項目 | 内容 |
| --- | --- |
| 形式 | プレーンテキスト（複数行可） |
| 上限 | **8,000 文字** |
| 必須 | 空文字・空白のみは受け付けない |
| 検証の位置 | **送信前に検証し、不合格なら外部 API を呼ばない**（費用が出ない位置で止める） |

> 上限の根拠は [notes/input-limit.md](./notes/input-limit.md) にある。実装の定数は `lib/validate.ts` の `MAX_INPUT_CHARS`。**値を変えるときは、必ず両方を直す。**

---

## 3. 出力

### 3-1 要約できた場合

| 項目 | 形式 |
| --- | --- |
| `summary` | 文字列。3行以内の要約 |
| `actions` | オブジェクトの配列。`task`（内容）・`owner`（担当者、不明なら `"未定"`）・`due`（期限、不明なら `"未定"`） |
| `actions` が 0 件 | **正常**。アクションの無い会議は現実にある |
| `requestId` | 文字列。問い合わせ時にログと突き合わせるための値 |

> 出力の型は `lib/types.ts` の `SummaryResult` と対応する。**片方を変えるときは、必ずもう片方も直す。**

### 3-2 失敗した場合

**失敗は次の7種類に分類する**（`lib/types.ts` の `FailureKind`）。分類ごとにリトライの可否が決まっている。

| `failureKind` | 意味 | リトライ |
| --- | --- | --- |
| `empty_input` | 空・空白のみ | **しない**（入力起因。何度やっても同じ） |
| `too_long` | 8,000 文字超過 | **しない**（同上） |
| `timeout` | 応答が返らない | する（一時的な事情） |
| `rate_limited` | レート制限 | する（同上） |
| `api_error` | それ以外の API 側の失敗 | する（同上） |
| `truncated` | 出力が上限に達して途中で切れた | する（同じ入力でも変わりうる） |
| `unparsable` | 形式が崩れてパースできない | する（同上） |

**失敗時は、利用者向けメッセージと `requestId` を返す。**スタックトレース・内部の詳細は画面に出さない。

## 4. 受け入れ基準

> **各基準は「正常系・合格条件・異常系」の3部品で書く**（`2-2-4`）。
> F の番号と名称は、教材本文の機能一覧（`2-1-0`）と揃えている。

### F-1 議事録を貼り付けて送信できる

| 部品 | 内容 |
| --- | --- |
| 正常系 | テキストエリアに議事録を貼り付け、「要約する」を押すと処理が始まる |
| 合格条件 | 送信中であることが画面に表示され、結果またはエラーが返る |
| 異常系 | 空・空白のみ・8,000 文字超は**送信前に**止め、外部 API を呼ばない。どの条件に当たったかを表示する |

**判定方法：**空文字・空白のみ・8,001 文字の3件を送り、いずれも外部 API が呼ばれないことを確認する（`tests/validate.test.ts`・`tests/route.test.ts`）。

---

### F-2 要約が返る

| 部品 | 内容 |
| --- | --- |
| 正常系 | 決定事項が含まれる議事録を送ると、`summary` が返り、画面に表示される |
| 合格条件 | `summary` が3行以内である |
| 異常系 | 形式不正（`unparsable`）・途中切れ（`truncated`）はリトライ（最大2回）後、分かるメッセージを返す |

**判定方法：**外部クライアントをモックに差し替え、正常応答・崩れた応答・途中で切れた応答の3通りで確かめる（`tests/parse.test.ts`・`tests/summarize.test.ts`）。

---

### F-3 アクション項目が返る

| 部品 | 内容 |
| --- | --- |
| 正常系 | ToDo が含まれる議事録を送ると、`actions[].task` / `owner` / `due` が一覧で表示される |
| 合格条件 | 各項目が担当・内容・期限を持つ。**担当者・期限が不明な項目は `"未定"`** になっている |
| 異常系 | **0件は正常。**「アクション項目はありません」と表示する |

**判定方法：**担当者の書かれていない ToDo を含む議事録と、ToDo の無い議事録の2通りをモックで確かめる（`tests/summarize.test.ts`）。

---

### F-4 失敗しても画面が壊れない

| 部品 | 内容 |
| --- | --- |
| 正常系 | ── |
| 合格条件 | 3章3-2の**すべての `failureKind`** について、① 例外を投げず、画面が操作可能なまま　② 何が起きたかが表示される　③ 次にどうするかが表示される |
| 異常系 | 500 系の内部詳細（スタックトレース等）を画面に出さない |

**判定方法：**外部クライアントをモックに差し替え、各 `failureKind` を発生させるテストを書く（`tests/route.test.ts`・`tests/retry.test.ts`。`2-4-13` と同じ形）。

---

### F-5 何が起きたかを後から追える

| 部品 | 内容 |
| --- | --- |
| 正常系 | 1リクエストにつき1行、構造化ログが出る |
| 合格条件 | ① `requestId` / `inputChars` / `inputTokens` / `outputTokens` / `durationMs` / `attempts` / `failureKind`（失敗時）/ `actionCount`（成功時）が記録される　② **議事録本文・API キー・利用者を特定できる情報が記録されない** |
| 異常系 | 入力検証で止めた場合も、`failureKind` 付きで1行記録される |

**判定方法：**ログの型（`lib/logger.ts` の `LogRecord`）に**本文を入れる欄を作らない**（`2-4-13`）。書こうとすると型で落ちる形にする（`tests/logger.test.ts`）。

## 5. 非機能の基準

| # | 観点 | 基準 | 判定方法 |
| --- | --- | --- | --- |
| 1 | **応答時間** | 1回の要約は**10秒以内**（目安） | 教材ではモックで検証。実測は試用時に行う |
| 2 | **リトライ** | **最大2回**（呼び出し総数3回）。**入力起因（`empty_input` / `too_long`）はリトライしない** | `tests/retry.test.ts` で呼び出し回数を数える |
| 3 | **キーの置き場所** | `ANTHROPIC_API_KEY` はサーバー側（Route Handler）のみ。**フロントに SDK もキーも置かない** | `components/SummarizeForm.tsx` がキー・SDK に触れていないことをコードで確認する |

## 7. やらないこと（合否に含めない）

| 項目 | 理由 |
| --- | --- |
| 要約文の「正しさ」の判定 | Constitution 第13条1（非決定的出力を自由に合否判定しない） |
| 音声ファイルの直接アップロード | 初版は貼り付けのみ |
| 議事録の保存・履歴 | 初版スコープ外 |
