# 実装手順書 ── 議事録要約アプリを1セッションで作る

> **この文書の位置づけ**：この完成形サンプルを、コーディングエージェント（Claude Code）への指示だけで、**1回のセッションで実装するための手順とプロンプト**をまとめたものです。
> 「何を作るか」は [requirements.md](../requirements.md)、「何で合否を決めるか」は [spec.md](../spec.md) にあります。**この文書は「どういう順番で・どう指示して作るか」だけを扱います。**
>
> 各ステップのプロンプトは、そのままコピーして使える形で書いてあります。ただし目的は暗記ではなく、**「なぜこの順番か」「なぜこの書き方か」を理解して、自分のアプリで同じ型を使えるようになること**です。

## 1. 始める前に ── 3点セットをそろえる

**実装のセッションを始めてよいのは、駆動開発の3点セットがそろってからです**（Constitution 第5条）。

| # | 3点セット | このアプリでは何か | 状態 |
| --- | --- | --- | --- |
| 1 | **ガードレール**（外枠） | 触ってよい範囲・守るルールを最初の指示で渡す（§3 ステップ0） | このセッションで渡す |
| 2 | **仕様**（判断基準） | [spec.md](../spec.md) の受け入れ基準 F-1〜F-5 | **確定済み** |
| 3 | **検証ループ**（収束） | `./scripts/verify`（コンテナ内で型チェック＋テスト）を各ステップの終わりに回す | このセッションで作る |

> ⚠️ **仕様が無いまま「議事録要約アプリを作って」と指示しないでください。**
> 動くものは出てきますが、**合否を判定する基準が無いので、出てきたものが正しいか誰にも分かりません。**Phase 1 で見た「意図しない実装」の入口です。

### 1-1 なぜ1セッションで完走できるのか

このアプリが1セッションで作れるのは、アプリが小さいからではなく、**判断がすべて事前に済んでいるから**です。

| 実装中に迷いそうなこと | どこで決着済みか |
| --- | --- |
| 入力の上限は何文字か | [spec.md](../spec.md) 2章（8,000 文字。根拠は [notes/input-limit.md](../notes/input-limit.md)） |
| 失敗をどう分類するか | [spec.md](../spec.md) 3-2（7種類の `failureKind`） |
| どの失敗をリトライするか | [spec.md](../spec.md) 3-2（入力起因はしない・最大2回） |
| ログに何を出すか・出さないか | [spec.md](../spec.md) F-5（本文・キーは出さない） |
| アクション0件は正常か | [spec.md](../spec.md) 3-1（**正常**） |

**セッション中にエージェントから質問が来たら、答えを口頭で返すのではなく、仕様書のどこに書いてあるかを示します。**書いていなければ、それは仕様の抜けです。実装を止めて仕様書に書き足してから続けます（基準の置き場所は仕様書1か所だけ・`2-3-6`）。

## 2. 実装の順番 ── 内側から外側へ

**依存の内側（純粋な関数）から外側（API・画面）へ向かって作ります。**

```
ステップ0  ガードレールを渡す（セッションの最初の指示）
ステップ1  types.ts       ── 出力の型。仕様3章をコードにする
ステップ2  validate.ts    ── 送る前に止める（F-1 の異常系）
ステップ3  prompt.ts      ── プロンプト＝仕様書（役割・出力形式・制約）
ステップ4  parse.ts       ── LLM の応答から形式だけを検証して取り出す
ステップ5  retry.ts       ── リトライしてよい失敗の切り分け
ステップ6  summarize.ts   ── 1〜5を束ねる。失敗を分類して返す
ステップ7  logger.ts      ── 構造化ログ（F-5）
ステップ8  route.ts       ── サーバー側の入口。キーはここだけ（2-4-11）
ステップ9  SummarizeForm  ── 画面。ローディング・エラー・空の3状態
ステップ10 仕上げ         ── 受け入れ基準 F-1〜F-5 との突き合わせ
```

### 2-1 なぜこの順番か

| 理由 | 説明 |
| --- | --- |
| **内側は外部なしでテストできる** | `validate` や `parse` は純粋な関数なので、API キーが無くてもテストが回る。**検証ループが最初から動く** |
| **1指示1部品にできる** | 部品の境界がファイルの境界と一致しているので、指示も確認も1部品ずつで済む。**一度に全部作らせると、レビューできない大きさの差分が返ってくる** |
| **画面は最後でよい** | 画面から作ると、動作確認のたびにブラウザ操作が要る。**ロジックをテストで固めてから画面を載せると、画面の確認は表示の確認だけになる** |

> 📌 **各ステップで「実装とテストを同時に」指示します。**
> あとでまとめてテストを書かせると、**実装に合わせたテスト**（通るためのテスト）が出てきます。仕様に合わせたテストにするため、同じ指示の中で仕様の該当箇所を参照させて書かせます。

## 3. 各ステップの指示プロンプト

**すべてのプロンプトは同じ型でできています。**

```
① 何を作るか（1部品）
② 参照する仕様（spec.md の該当箇所）
③ 制約（やらないこと・置いてはいけない場所）
④ 確認方法（テスト・実行するコマンド）
```

この4点のうち、受講生が書き忘れやすいのは**③と④**です。③が無いとエージェントは親切に範囲を広げ、④が無いと「書きました」で終わります。

### ステップ0 ガードレールを渡す

**セッションの最初に1回だけ、全体のルールを渡します。**個々の部品の指示より先です。

```
議事録要約アプリを実装します。まずこのセッション全体のルールを確認してください。

【仕様】
- docs/spec.md が唯一の判断基準です。実装で迷ったら spec.md を参照し、
  書かれていないことは私に質問してください。推測で決めないでください。
- docs/requirements.md は背景の理解に使ってください。合否には使いません。

【構成のルール】
- サーバー側は app/api/summarize/route.ts のみ。API キーと SDK に触れるのは
  ここから呼ばれるコードだけです。
- components/ 以下（ブラウザ側）には、API キーも @anthropic-ai/sdk の import も
  置いてはいけません。
- 部品は lib/ に置き、1ファイル1責務にします。

【進め方のルール】
- 私が指示した部品だけを作ってください。次の部品に勝手に進まないでください。
- 各部品は、実装とテスト（tests/）をセットで作ってください。
- テストは外部 API を呼ばず、モックで完結させてください。
- 各ステップの終わりに ./scripts/verify（型チェック＋テスト。コンテナ内で
  実行されます）を実行し、結果を見せてください。npm コマンドをホストで
  直接実行しないでください。

まだ実装は始めないでください。このルールで進められるか、不明点があれば
先に質問してください。
```

**このプロンプトの要点：**

| 行 | なぜ書くか |
| --- | --- |
| 「spec.md が唯一の判断基準」 | 基準の置き場所を1か所にする（`2-3-6`）。エージェントが web の一般論で判断するのを防ぐ |
| 「推測で決めないでください」 | 仕様の抜けを**質問として表面化**させる。黙って埋められると、どこが推測か分からなくなる |
| 「指示した部品だけ」「勝手に進まない」 | 1指示1部品を守らせる。**確認が追いつく速度に抑える** |
| 「モックで完結」 | 検証ループに費用とキーを不要にする。**テストのたびに API 料金が出る構成にしない** |
| 「まだ実装は始めない」 | ルールの確認と実装を分ける。**最初の応答で理解のずれを見つける** |

### ステップ1 types.ts ── 仕様3章を型にする

```
lib/types.ts を作ってください。

【作るもの】
- docs/spec.md「3. 出力」に対応する型：
  - ActionItem（owner / task / due。いずれも文字列）
  - SummaryResult（summary と actions: ActionItem[]）
- docs/spec.md「3-2 失敗した場合」の7分類に対応する FailureKind
  （empty_input / too_long / timeout / rate_limited / truncated /
   unparsable / api_error のユニオン型）

【制約】
- 各フィールドに、仕様のどの記述に対応するかをコメントで1行書いてください。
- 「spec.md を変えるときはこのファイルも直す」と分かるコメントを
  ファイル先頭に置いてください。

【確認】
- ./scripts/verify で型チェックが通ること。
```

> 📌 **最初に型を作るのは、以降のすべての部品の「共通の語彙」になるからです。**
> `FailureKind` を最初に固定しておくと、validate も retry も logger も同じ7分類の上で作られます。**あとから分類を思いつきで増やす事故がなくなります。**

**確認すること：**

- [ ] 7分類が spec.md 3-2 と1つずつ一致している（多くも少なくもない）
- [ ] 型とスペックの対応がコメントで追える

### ステップ2 validate.ts ── 送る前に止める

```
lib/validate.ts と tests/validate.test.ts を作ってください。

【作るもの】
- validateInput(raw: unknown): 入力を検証する関数
- docs/spec.md「2. 入力」が基準です：
  - 空・空白のみ → kind: "empty_input" で不合格
  - 8,000 文字超 → kind: "too_long" で不合格
  - 上限の定数は MAX_INPUT_CHARS として export し、根拠が
    docs/notes/input-limit.md にあることをコメントで示す
- 不合格時は、利用者に見せられる日本語の message を含めてください。

【制約】
- この関数は純粋関数にしてください。外部 API・環境変数に触れないこと。

【確認】
- テストは最低4件：空文字／空白のみ／8,000 文字ちょうど（合格）／
  8,001 文字（不合格）。境界の内側と外側を両方入れてください。
```

> 📌 **「8,000 ちょうど」と「8,001」を分けて指示しているのは、境界のテストを書かせるためです。**
> 「上限超過のテストを書いて」だけだと、10,000 文字のような**境界から遠いテスト**が1件出てくるだけのことがあります。境界は自分で指定します。

**確認すること：**

- [ ] 検証が **API を呼ぶ前**の位置にある（spec.md 2章「検証の位置」）
- [ ] 上限の数値がテストと実装で二重管理になっていない（定数を参照している）

### ステップ3 prompt.ts ── プロンプト＝仕様書

```
lib/prompt.ts を作ってください。

【作るもの】
- SYSTEM_PROMPT：LLM への指示。役割・出力形式・制約の3点を含めること。
  - 出力形式：docs/spec.md「3-1」と同じ形の JSON（summary / actions）を、
    JSON だけで返させる（前後に説明文を付けさせない）
  - 制約として必ず入れる：
    - summary は3行以内
    - actions は議事録に書かれていることだけ。推測で足さない
    - アクションが無い議事録なら actions は空配列（0件は正常）
    - owner・due が読み取れなければ "未定"
- buildUserMessage(minutes)：議事録本文を渡すユーザーメッセージ

【制約】
- プロンプトを変えたら spec.md と types.ts との整合を確認する、という
  コメントをファイルに残してください。

【確認】
- SYSTEM_PROMPT の制約が spec.md の 3-1 と1対1で対応しているか、
  対応表を出力して見せてください。
```

> 📌 **プロンプトも仕様の一部です**（`2-4-12`）。
> 「0件は正常」「未定で埋める」は spec.md の決定です。**プロンプトに書き忘れると、LLM が気を利かせてアクションを推測で作ります。**その出力は形式としては合格してしまうので、テストでは捕まえられません。だからプロンプト側で止めます。

### ステップ4 parse.ts ── 形式だけを検証する

```
lib/parse.ts と tests/parse.test.ts を作ってください。

【作るもの】
- parseSummary(raw: string)：LLM の応答テキストから SummaryResult を
  取り出す関数。成功なら { ok: true, value }、失敗なら
  { ok: false, reason } を返す。
- 検証するのは形式だけです：
  - JSON が取り出せるか（前後に余計なテキストが付いていても拾う）
  - summary が空でない文字列か
  - actions が配列か、各要素がオブジェクトか
  - owner / task / due が欠けている要素は "未定" で埋める（落とさない）

【制約】
- 要約の「内容が正しいか」は検証しないでください。docs/spec.md
  「7. やらないこと」のとおり、内容の正しさは合否に含めません。
  検証できるのは形式だけです。

【確認】
- テストには最低限、次を含めてください：
  正常な JSON／JSON の前後に説明文が付いた応答／JSON でない応答／
  summary が欠けた応答／actions の要素から owner が欠けた応答（未定で
  埋まること）／actions が空配列（ok になること）
```

> 📌 **「欠けたフィールドは落とさずに未定で埋める」は、仕様の決定をコードに写した箇所です。**
> エージェントに任せると「不正な要素はスキップする」実装がよく出てきます。もっともらしいですが、**仕様は「不明なら未定」と決めています。**指示に書かなければ、仕様と違う「もっともらしい実装」が通ってしまいます。

### ステップ5 retry.ts ── リトライの切り分け

```
lib/retry.ts と tests/retry.test.ts を作ってください。

【作るもの】
- isRetriable(kind: FailureKind): boolean
  docs/spec.md「3-2 失敗した場合」の表のとおりに切り分けます：
  - リトライしない：empty_input / too_long（入力起因。何度やっても同じ）
  - リトライする：timeout / rate_limited / api_error / truncated / unparsable
- withRetry：最大リトライ回数と待ち時間を受け取り、リトライしてよい
  失敗のときだけ再実行する関数。
  - 既定は最大2回（呼び出し総数3回）。spec.md「5. 非機能の基準」の2です。
  - 待ち時間は回を追うごとに倍にする。
  - sleep はテストから差し替えられる形にしてください。

【確認】
- テストで確認すること：
  - 入力起因の失敗が1回で打ち切られる（呼び出し回数を数える）
  - リトライ対象の失敗が最大3回で打ち切られる
  - 2回目で成功したら3回目を呼ばない
```

> 📌 **「入力起因はリトライしない」の理由まで理解してください。**
> 8,001 文字の入力は、何回送っても 8,001 文字です。**リトライは費用を捨てるだけ**（`2-4-13`）。この切り分けを型（`FailureKind`）の上でやるので、新しい失敗分類を足すときに switch 文が漏れを教えてくれます。

### ステップ6 summarize.ts ── 部品を束ねる

```
lib/summarize.ts と tests/summarize.test.ts を作ってください。

【作るもの】
- summarize(client, minutes, opts)：prompt → API 呼び出し → parse を
  withRetry の中で回し、成功なら SummaryResult、失敗なら
  FailureKind 付きの結果を返す関数。
- 失敗の分類：
  - API の例外 → timeout / rate_limited / api_error に分類
  - stop_reason が max_tokens → truncated（出力が途中で切れている）
  - 応答が空 → api_error
  - parse 失敗 → unparsable
- usage から inputTokens / outputTokens を取り出して結果に含める
  （ログで使います）。

【制約】
- Anthropic のクライアント全体に依存せず、messages.create だけを持つ
  最小のインターフェース（MessagesClient）を定義して、それに依存して
  ください。テストではそのインターフェースをモックします。
- モデル名と max_tokens は定数として export してください。

【確認】
- テストは実 API を呼ばないこと。モックで次を確認：
  正常応答／崩れた JSON（リトライ後 unparsable）／max_tokens で切れた
  応答（truncated）／API 例外の分類。
```

> 📌 **「SDK 全体ではなく最小のインターフェースに依存する」が、この部品の設計の要点です。**
> `messages.create` しか使わないのに SDK の型全体に依存すると、テストのモックが大きくなります。**使う分だけのインターフェースを切ると、モックは数行で済みます。**`3-3-9` で学ぶ「インターフェース差し替え」の先取りです。

lib/logger.ts と tests/logger.test.ts を作ってください。

【確認】

### ステップ8 route.ts ── サーバー側の入口

```
app/api/summarize/route.ts を作り、tests/route.test.ts を書いてください。

【作るもの】
- POST /api/summarize：
  1. validateInput で検証。不合格なら 400 と利用者向け message を返し、
     API は呼ばない。このときもログを1行出す（failureKind 付き）
  2. summarize を呼ぶ
  3. 失敗なら 502。利用者向け message と requestId だけを返し、
     内部の詳細（スタックトレース等）は返さない
  4. 成功なら SummaryResult と requestId を返す
  5. 成否どちらも構造化ログを1行出す（docs/spec.md F-5 の項目）

【制約】
- API キー（ANTHROPIC_API_KEY）は環境変数から読み、このファイルの
  外に出さないでください（2-4-11）。
- レスポンスに e.message や e.stack をそのまま入れないでください。

【確認】
- テストで確認すること（クライアントはモック）：
  - 空入力で 400 が返り、モックの messages.create が呼ばれていない
  - 失敗時のレスポンス body に内部情報が含まれない
  - 成功・失敗どちらでもログが1行出る
```

> ⚠️ **「空入力で 400、かつ API が呼ばれていない」の2つ目まで確認するのが要点です。**
> 400 が返ることだけ確認すると、「呼んでから失敗した」実装でも通ってしまいます。**費用が出ない位置で止まっていること**まで確かめます（spec.md F-1 の判定方法）。

### ステップ9 SummarizeForm ── 画面

```
components/SummarizeForm.tsx と app/page.tsx を作ってください。

【作るもの】
- 議事録を貼り付けるテキストエリアと「要約する」ボタン
- 状態は idle / loading / done / error の4つ。
  - loading：ボタンを無効化し、処理中の表示を出す（F-1）
  - error：何が起きたかの message と「もう一度試す」導線（F-4）
  - done：summary と actions の一覧。actions が0件のときは
    「アクション項目はありません」と表示する（F-3 の異常系）
- fetch 自体が失敗した場合も、画面は操作可能なままエラー表示にする

【制約】
- このファイルに API キー・@anthropic-ai/sdk の import を置かないこと
  （2-4-11）。サーバーとのやり取りは fetch("/api/summarize") だけです。
- owner / due の "未定" はそのまま表示してください（画面側で推測して
  埋め直さない）。

【確認】
- ./scripts/verify のあと、アプリを起動し、次の3つを手で確認：
  空のまま送信／正常な議事録／（開発者ツールでオフラインにして）通信失敗。
  （起動の手順は本手順書の 4-4 を参照。この構成の既定は Docker で
  ./scripts/dev → http://localhost:3000 です）
```

> 📌 **ローディング・エラー・空の3状態を最初から指示に入れます**（`2-4-13`）。
> 「フォームを作って」だけだと、正常系だけの画面が返ってきます。**3状態はあとから足すより、最初から作らせるほうが差分が小さい**です。

## 4. セッション運びのコツ

### 4-1 指示の型を崩さない

**どの部品でも、指示は同じ4点で書きます。**

| 部品 | 書き忘れると何が起きるか |
| --- | --- |
| ① 何を作るか | ── |
| ② 参照する仕様 | エージェントが web の一般論で判断し、仕様と違う「もっともらしい実装」が返る |
| ③ やらないこと | 頼んでいない機能・頼んでいないファイルの変更が混ざり、差分が読めなくなる |
| ④ 確認方法 | 「書きました」で終わり、動くかどうかは次のステップで発覚する |

### 4-2 エージェントの質問は仕様への入口

セッション中に「上限を超えたときのメッセージはどうしますか」のような質問が来たら、**それは仕様の抜けが見つかった瞬間です。**その場の思いつきで答えず、spec.md に書き足してから「spec.md の◯章に追記したので、それに従ってください」と返します。**口頭で答えると、決定が会話ログにしか残りません。**

### 4-3 各ステップの終わりに必ず検証ループを回す

```bash
./scripts/verify   # 型チェック＋テスト（中身は docker compose run --rm app npm run verify）
```

**赤のまま次のステップへ進まないでください。**2ステップ先で赤くなったとき、原因の候補が2ステップ分に増えます。1ステップずつ緑に戻すのが、結局いちばん速い進め方です。

### 4-4 費用とキーの扱い

| 場面 | キー | 費用 |
| --- | --- | --- |
| ステップ1〜10 の実装とテスト | **不要**（すべてモック） | 0円 |
| 最後の手動確認（`./scripts/dev`） | `ANTHROPIC_API_KEY` を環境変数で渡す | 数円程度 |

**テストが API キー無しで回る構成にしたのは偶然ではなく、ステップ0とステップ6の指示（モックで完結・最小インターフェース）の結果です。**

#### 必要な環境変数

このアプリが使う環境変数は1つだけです。

| 変数名 | 用途 | 読む場所 | 取得先 |
| --- | --- | --- | --- |
| `ANTHROPIC_API_KEY` | Anthropic API の認証 | `app/api/summarize/route.ts`（**サーバー側のみ**） | Anthropic Console で作成（`2-4-10`）。**作成時に一度しか表示されない** |

> ⚠️ **`NEXT_PUBLIC_` を付けた変数に、キーを入れてはいけません**（`2-4-11`）。
> `NEXT_PUBLIC_` はビルド時にブラウザへ配られる印です。**「公開される印」であって「保護される印」ではありません。**

#### キーの設定手順（ステップ9 の手動確認の前に）

**1. テンプレートから `.env.local` を作る**

リポジトリ直下に [.env.example](../../.env.example) を置いてあります。コピーして値を書きます。

```bash
cp .env.example .env.local
```

```bash
# .env.local  ← このファイルはリポジトリに入れない
ANTHROPIC_API_KEY=〔Console で作ったキー〕
```

**2. リポジトリに入らないことを確認する**（`2-4-11`）

```bash
git check-ignore -v .env.local
```

| 結果 | 意味 |
| --- | --- |
| `.gitignore:〔行番号〕:.env*.local　.env.local` のように出る | **除外されている。正しい** |
| **何も出ない** | **除外されていない。コミットする前に必ず直す** |

**3. 起動する**

| 起動方法 | キーの読まれ方 |
| --- | --- |
| `./scripts/dev`（**既定**。中身は `docker compose up`） | `compose.yaml` の `env_file` が `.env.local` を読む |
| `npm run dev`（ホストで直接・**非推奨・旧手順**） | Next.js が `.env.local` を自動で読む |

どちらの場合も、置き場所は同じ `.env.local` の1か所です。**シェルの `export` やコマンドラインにキーを直接書く方法は使いません**（コマンド履歴に残ります）。

#### 起動は Docker で行う（既定）

**このサンプルは、ホストに Node.js も `node_modules` も入れない方針です**（アプリの [README.md](../../README.md)）。依存はコンテナ内の名前付きボリュームにだけ入っているため、ホストでそのまま `npm run dev` を打つと `next: command not found` や `Cannot find module` の類いで失敗します。**これは異常ではなく、この構成の既定の状態です。**起動は Docker で行います。

```bash
docker compose build     # 初回のみ。依存の取得（npm install）を含む
./scripts/dev            # コンテナ内で開発サーバーが起動する（中身は docker compose up）
```

1. 起動ログに `Ready` 系の表示が出たら、**ブラウザで http://localhost:3000 を開く**
2. 議事録を貼り付けて1回要約し、動作を確かめる（`.env.local` は `compose.yaml` の `env_file` 経由でコンテナに渡っています）
3. 終了は **Ctrl+C**。コンテナを片付けるときは `docker compose down`

**テスト（判定器）も同じく Docker 経由です。**

```bash
./scripts/verify   # 型チェック＋テスト（中身は docker compose run --rm app npm run verify）
```

#### ホストで `npm run dev` したい場合（非推奨・旧手順）

**非推奨の旧手順です。**ホストに Node.js と `node_modules` が入るため、このサンプルの「ホストに入れない」方針からは外れます。Docker が使えない事情がある場合に限り、それを理解したうえで行ってください。

1. **Node.js を用意する。**コンテナと同じ **Node.js 22 系**（`Dockerfile` の `node:22`）を推奨。Next.js が要求するバージョンは変わることがあるため、[Next.js 公式の動作要件](https://nextjs.org/docs/app/getting-started/installation)を確認してください（参照日 2026-08-28）
2. **依存をホストに入れる**：`npm install`（`node_modules/` がホストに作られます。`.gitignore` 済みなのでコミットには入りません）
3. **起動する**：`npm run dev` → ブラウザで http://localhost:3000 を開く

> 💡 **あとで Docker に戻っても衝突しません。**
> コンテナは名前付きボリュームの `node_modules` を使い、ホスト側のものは見ません（`compose.yaml` のコメント参照）。ホストを元の状態に戻したいときは `rm -rf node_modules` で削除します。

#### Vercel への登録（公開まで進める場合）

デプロイはこの手順書のスコープ外ですが、公開するときの環境変数の手順だけ載せておきます（詳細は `2-5-16`）。

1. Vercel の **Settings → Environment Variables** で `ANTHROPIC_API_KEY` を登録する（項目の名前と場所は変わることがあります。画面表示を正としてください）
2. **Production に適用されているか**（チェックが入っているか）を確認する
3. **登録した「あと」に再デプロイする。**登録前のデプロイには反映されていません（「登録したのに動かない」の大半はこれです）
4. 公開 URL で1回動かして反映を確かめ、**公開ページの JavaScript に `sk-ant` が無いことを検索で確認する**（あればキーを失効させる・`2-4-11`）

## 5. この手順を自分のアプリに使うとき

このアプリ固有なのはステップ3（プロンプト）とステップ9（画面の項目）だけで、**それ以外の型はそのまま使い回せます。**

1. 仕様（受け入れ基準）を先に確定する ── 無ければセッションを始めない
2. ステップ0のガードレールを、自分のアプリのファイル構成に合わせて書き換える
3. 部品を「純粋な関数 → 外部を呼ぶ関数 → API → 画面」の順に分ける
4. 1部品ずつ「①作るもの ②参照する仕様 ③やらないこと ④確認方法」で指示する
5. 各ステップの終わりに検証ループを回し、緑に戻してから次へ進む
6. 最後に、テストの緑とは別に、仕様書との突き合わせを自分の目でやる
