# 一気通貫の実装ガイド ── 1回の指示で完成まで走らせるためのリポジトリ設計

> **この文書の位置づけ**：[README.md](./README.md)（実装手順書）は、人が**1部品ずつ指示して**このアプリを作る型でした。この文書はその発展形です。**セッションの中で人が口頭でやっていた判断・進行管理・確認を、あらかじめリポジトリ内のファイルへ移しておき、「PLANS.md に従って完成まで進めてください」という1回の指示でコーディングエージェント（Claude Code）に完走させる**ためのセッティングをまとめます。
>
> 使う道具は新しいものではありません。**Phase 2 の各節で作ったもの（ガードレール・仕様・PLANS.md・ルール設計・判定器）を、1つのリポジトリに組み合わせるだけ**です。どの設定がどの節と対応するかを、各所に明記してあります。

| 最終更新 | 2026-09-02 |

## 1. 何が「一気に」を可能にするのか

**先に結論です。エージェントが賢いから一気に作れるのではありません。セッション中に人がやっていた判断を、すべてファイルに置き換えてあるから、人を待たずにループが回るのです。**

[README.md](./README.md) の逐次型では、次のことを毎ステップ人がやっていました。それぞれを、リポジトリ内のファイルに移します。

| 逐次型でセッション中に人がやっていたこと | 一気通貫型では何に置き換わるか | 対応する節 |
| --- | --- | --- |
| 「次はこの部品を作って」と順番を指示する | **`PLANS.md`** のタスクと順番 | `2-3-6`・`2-3-7` |
| 「合格の基準は spec.md の◯章」と都度参照させる | **`docs/spec.md`**（判断基準の唯一の置き場所） | `2-2-3`・`2-2-4` |
| 「フロントにキーを置くな」等をステップ0で言い聞かせる | **`CLAUDE.md`**（毎セッション自動で読み込まれるルール） | `2-5-15` |
| 危険な操作が来たら目視で止める | **`.claude/settings.json`** のパーミッション | `0-2-5`・`2-5-15` |
| 「テストを回して結果を見せて」と言う | **`./scripts/verify`**（判定器の入口。コンテナ内で型チェック＋テスト） | `2-1-2` |
| 「そのステップは完了」と判定して次に進ませる | **PLANS.md の完了条件**（機械で判定できる形で書く） | `2-3-7` |
| おかしくなったら手で止める | **停止条件**（PLANS.md のリスク欄・CLAUDE.md） | `2-1-1`・`2-1-2` |

**「各手順が自動で実装できる」の正体はこの表です。**1行ずつ見ると、どの手順も「人の記憶と注意」を「ファイルと機械の判定」に置き換えているだけです。逆に言うと、**この表のどれか1つでも口頭のまま残っていると、そこで毎回セッションが止まります。**

## 2. リポジトリに置くファイル一式

一気通貫で走らせる直前のリポジトリは、次の状態になっています。

```
minutes-app/
├── CLAUDE.md                 ← ガードレール（毎セッション読み込まれる）… §3-2
├── PLANS.md                  ← 実行計画（順番・完了条件・停止条件）… §5
├── .claude/
│   └── settings.json         ← パーミッション（deny / ask / allow）… §3-3
├── .gitignore                ← .env を必ず含める（2-4-11）
├── .env.example              ← 環境変数のテンプレート（値は書かない）… §8
├── Dockerfile / compose.yaml ← 実行環境（Node・依存・判定器はコンテナ内だけ）
├── scripts/                  ← 入口ラッパー（verify / dev / install）… §4
├── package.json              ← "verify": "tsc --noEmit && vitest run" … §4
├── docs/
│   ├── requirements.md       ← 何を・なぜ作るか（確定済み）
│   ├── spec.md               ← 受け入れ基準 F-1〜F-5（確定済み）
│   ├── loop.md               ← ループ設計（判定器・打ち切り条件）… §3
│   └── notes/input-limit.md  ← 数値の根拠（2-2-5 で逃した補足）
├── lib/ , app/ , components/ ← これから作られる（実装は空でよい）
└── tests/                    ← これから作られる
```

**要点は、実装コードが1行も無い状態でも、仕様・計画・ルール・判定器の4つは先に全部そろっていることです。**本文が先で枠が後だと、枠に合わない実装を後から直すことになります。

## 3. ガードレールの設定方法 ── 3層のどこに何を置くか

**ガードレールは「気をつける」ではなく構造で守るもので、置ける場所が3層あります**（`2-1-1`）。一気通貫では人が途中にいないので、**どの事故をどの層で止めるかの割り当てが、逐次型よりも重要になります。**

| 層 | このリポジトリでの実体 | いつ止まるか |
| --- | --- | --- |
| **① 設定** | `.claude/settings.json`・`CLAUDE.md`・`.gitignore` | **実行される前**（そもそも起きない） |
| **② プロセス** | `PLANS.md` の完了条件・終了後の差分レビュー（§9） | 作業の途中・直後（人が見る場所を決める） |
| **③ コード** | `tsconfig.json`（`strict: true`）・`tests/`・`./scripts/verify` | **実行した直後**（機械が検知する） |

割り当ての基準は「取り返しがつくか」です（`2-1-1`）。

| 事故 | 層 | 置き場所 |
| --- | --- | --- |
| API キーが会話・ログ・コードに出る（不可逆） | ① | `settings.json` の `deny` ＋ `.gitignore` |
| ファイルが消える（不可逆） | ① | `settings.json` の `deny` |
| 本番に意図しないものが出る・依存が勝手に増える（不可逆寄り） | ① | `settings.json` の `ask` |
| 型が合わない・テストが落ちたまま進む（戻せるが積み上がる） | ③ | `./scripts/verify`（判定器の入口） |
| 頼んでいない範囲の変更・設計の妥当性（機械で判定できない） | ② | `CLAUDE.md` の宣言＋終了後の差分レビュー |

> ⚠️ **層を取り違えると効きません**（`2-1-1`）。
> 「キーを読ませない」を CLAUDE.md（お願い）に書いても止まりません。パーミッション（①）で止めます。逆に「命名の一貫性」はパーミッションでは止められません。人が見る場所（②）に置きます。

### 3-1 まず guardrails.md を書いてから、設定に変換する

`2-1-1` のハンズオンで作った **`docs/guardrails.md`（禁止事項・確認ポイント・停止条件）が設計図**で、CLAUDE.md と settings.json は**それを実行可能な形に変換したもの**です（`2-5-15`）。検証ループの側は **`docs/loop.md`**（`2-1-2` で作るループ設計。判定器・人が見る場所・打ち切り条件）が設計図で、CLAUDE.md「検証ループ」の変換元になります。このアプリでは次の3つが核になります。

| guardrails.md（言葉） | 変換先 |
| --- | --- |
| `.env` と鍵を読ませない・キーをフロントに書かせない | `settings.json` の `deny` ＋ CLAUDE.md の構成ルール |
| 落ちたテストを削除・期待値の緩和で通させない | CLAUDE.md「触ってはいけないもの」 |
| 同じエラー3回で手を止める・10ファイル超は分割 | CLAUDE.md と PLANS.md の停止条件 |

### 3-2 CLAUDE.md の内容（このアプリ版の実例）

**[README.md](./README.md) ステップ0で毎回打っていたガードレールのプロンプトを、そのままファイルにしたものです。**ファイルにすると、毎セッション自動で読み込まれ、打ち忘れが消えます。

```markdown
# 議事録要約アプリ 開発ルール

## 仕様

- `docs/spec.md` が唯一の判断基準。迷ったら spec.md を参照し、
  書かれていないことは推測せず、質問として報告する。
- `docs/requirements.md` は背景の理解に使う。合否には使わない。

## 構成のルール

- サーバー側は `app/api/summarize/route.ts` のみ。API キーと SDK に
  触れるのはここから呼ばれるコードだけ。
- `components/` 以下に API キー・`@anthropic-ai/sdk` の import を置かない。
- 部品は `lib/` に置き、1ファイル1責務にする。

## 変更の範囲

- タスクを始める前に、変更するファイルの一覧を出す。一覧に無い
  ファイルは変更しない。
- 依頼された範囲を超える変更（似た箇所の一括修正・リファクタ）は、
  提案として挙げるだけにして、実行しない。
- 1タスクで 10 ファイルを超える変更が必要になったら、止めて分割を提案する。

## 触ってはいけないもの

- テストの削除をしない。期待値を緩めない。テストが落ちたら、まず実装を疑う。
- `.env`・`.env.local` を読まない、書かない。
- `package.json` の依存を、理由の説明なしに追加・変更しない。
- `docs/spec.md` の受け入れ基準を、実装に合わせて書き換えない。

## 検証ループ

- 各タスクの終わりに `./scripts/verify`（ラッパー経由でコンテナ内実行）を実行し、
  緑に戻してから次へ進む。
- ホストに Node.js や node_modules は不要。判定器はコンテナ内で動く。
  素の `npm run …` をホストで実行しない。
- テストは外部 API を呼ばず、モックで完結させる。

## 確認を挟むこと（実行前に何をするかを述べて、承認を待つ）

- ファイルの削除
- 依存パッケージの追加
- 環境変数・デプロイ設定の変更
- API を呼ぶ回数が増える変更（リトライ回数・並列化）

## 停止条件（ここまで来たら手を止めて報告する）

- 同じエラーの修正を3回試して直らない
- 仕様に書かれていない判断が必要になった
```

**書き方の要点**（`2-5-15`）：

| 要点 | 説明 |
| --- | --- |
| 「〜しない」だけでなく「〜する」を書く | 「テストを消さない」だけだと代わりの行動が決まらない。「**まず実装を疑う**」まで書く |
| 判断基準は書かず、spec.md を指す | 基準の置き場所は1か所（`2-3-6`）。CLAUDE.md に基準を写すと、二重管理になって食い違う |
| 費用が増える変更を「確認を挟むこと」に入れる | 呼び出し回数の増加は費用の増加（`2-4-10`）。「リトライを5回にしました」が黙って入るのを防ぐ |

### 3-3 .claude/settings.json の内容（パーミッション）

**`2-5-15` で作った設定をそのまま使います。**

```json
{
  "permissions": {
    "allow": [
      "Bash(./scripts/verify)",
      "Bash(./scripts/dev)",
      "Bash(docker compose run --rm app *)",
      "Bash(docker compose up *)",
      "Bash(git status)",
      "Bash(git diff *)"
    ],
    "ask": [
      "Bash(./scripts/install)",
      "Bash(docker compose build *)",
      "Bash(git push *)",
      "Bash(vercel *)"
    ],
    "deny": [
      "Read(./.env)",
      "Read(./.env.*)",
      "Bash(npm *)",
      "Bash(rm *)"
    ]
  }
}
```

| 区分 | 何が入るか | 一気通貫での意味 |
| --- | --- | --- |
| `deny` | 不可逆で、起きたら取り返しがつかないもの＋**ホスト npm の誤実行** | 人が見ていなくても**そもそも実行されない** |
| `ask` | 不可逆寄りだが、正当な場面もあるもの（依存の再取得・イメージ再構築・公開系） | ここだけは**人の承認で止まる**。一気通貫でも残す |
| `allow` | 判定器と状態確認（すべて**ラッパーまたは compose 経由**） | **確認なしで何度でも回る。ループが自走する条件** |

> ⚠️ **`Bash(npm *)` を `deny` に入れてあります。**
> このリポジトリの Node.js と依存は**コンテナ内にしかありません**。エージェントがホストで `npm run …` を打っても失敗するだけでなく、`npm install` が通ってしまうとホストに `node_modules` が作られ、「ホストに入れない」という方針が崩れます。**npm 系はラッパー（`./scripts/*`）か `docker compose run` 経由だけを許可**し、ホスト直叩きの経路を設定で塞ぎます。

> ⚠️ **一気通貫では `allow` が主役です。**
> 逐次型なら確認プロンプトが多くても人がその場で承認しながら進めますが、一気通貫では**判定器（`./scripts/verify`）に確認が挟まるたびにループが止まります。**止めすぎた設定は外されて無意味になる（`0-2-5`）、の実例です。逆に `ask` を空にしてはいけません。**依存の追加とデプロイまで自走させると、「完成しました」の中身を誰も確認していないことになります。**

## 4. コード規約とリンター ── 規約は文章ではなく判定器に落とす

**このリポジトリに「コーディング規約.md」はありません。規約は文章で書かず、機械が判定できる形（③コード層）に落としてあります**（`2-1-2` 判定器）。

| 規約として守らせたいこと | 判定器としての実体 |
| --- | --- |
| 型を正しく付ける・`any` に逃げない | `tsconfig.json` の `strict: true` ＋ `tsc --noEmit` |
| 仕様の挙動を守る（境界・異常系・ログ） | `tests/` の6ファイル（vitest） |
| ログに本文を出さない | `LogRecord` 型に**本文のフィールドが無い**（書くと型エラー） |
| 上記すべてを1コマンドで判定する | **`./scripts/verify`**（コンテナ内で `tsc --noEmit && vitest run` を実行） |

**1コマンドに束ねるのが要点です。**理由は2つあります。

1. **エージェントへの指示が「verify を回せ」の1行で済む。**「型チェックして、テストして、Lint して…」と列挙すると、どれかが抜けます。
2. **`allow` の登録も1行で済む。**判定器が3コマンドに分かれていると、allow の管理も3倍になります。

> 💡 **ESLint / Prettier を足す場合も、同じ考え方で `verify` に連結します。**
> 例：`"verify": "tsc --noEmit && eslint . --max-warnings 0 && vitest run"`。このサンプルは教材の範囲を型とテストに絞っているため Lint を入れていませんが、**入れる場合の置き場所は「新しいルール文書」ではなく「判定器への連結」です。**なお、Lint でも判定できないもの（命名の妥当性・設計の良し悪し）は③層では守れません。②層＝終了後の人のレビュー（§9）に残します。

**もう1つの前提が、テストがモックで完結していることです**（[README.md](./README.md) ステップ6の `MessagesClient`）。判定器が API キーと費用を要求する構成だと、無人でループを回せません。**キー無し・0円で何百回でも回る判定器**が、一気通貫の土台です。

## 5. PLANS.md の作り方

**`2-3-7` のテンプレート（目的・スコープ・タスク・完了条件・決定事項・リスクの6項目）に、[README.md](./README.md) の実装順を落とします。**逐次型で人が出していた「次はこれ」という指示が、ここに全部書かれている状態を作ります。

```markdown
# 議事録要約アプリ 実装計画

## 1. 目的

docs/spec.md の受け入れ基準 F-1〜F-5 を満たす議事録要約アプリを実装し、
./scripts/verify が緑の状態で完了報告する。

## 2. スコープ

**やること**：lib / app / components / tests の実装一式
**やらないこと**：docs/spec.md「7. やらないこと」のとおり
（保存・履歴、音声、要約内容の正しさの判定）。デプロイもこの計画では行わない。

## 3. タスク

- [ ] T1 lib/types.ts ── spec 3章の型と FailureKind（7分類）
- [ ] T2 lib/validate.ts ＋テスト ── 空・空白のみ・8,000 文字境界
- [ ] T3 lib/prompt.ts ── 役割・出力形式・制約（0件は空配列、不明は「未定」）
- [ ] T4 lib/parse.ts ＋テスト ── 形式だけを検証。欠けは「未定」で埋める
- [ ] T5 lib/retry.ts ＋テスト ── 入力起因はリトライしない。最大2回
- [ ] T6 lib/summarize.ts ＋テスト ── MessagesClient 最小インターフェース
- [ ] T7 lib/logger.ts ＋テスト ── LogRecord に本文のフィールドを作らない
- [ ] T8 app/api/summarize/route.ts ＋テスト ── 400 は API 未呼び出し
- [ ] T9 components/SummarizeForm.tsx ＋ app/page.tsx ── 3状態の画面
- [ ] T10 突き合わせ ── F-1〜F-5 と実装・テストの対応表を作る

## 4. 完了条件

| タスク | 完了と言える条件 |
| --- | --- |
| T1〜T9 共通 | ./scripts/verify が緑。テストは外部 API を呼んでいない |
| T2 | 空・空白のみ・8,000 ちょうど・8,001 の4件のテストが通る |
| T5 | 呼び出し回数を数えるテストで、入力起因1回・その他最大3回 |
| T8 | 空入力で 400、かつモックの messages.create が未呼び出し |
| T10 | F-1〜F-5 の各行に実装ファイルとテストファイルが埋まっている |

## 5. 決定事項

| # | 決めたこと | 選ばなかった案 | 理由 |
| --- | --- | --- | --- |
| D1 | 検証は送信前（validate） | API 応答後にエラー処理 | 費用が出ない位置で止める |
| D2 | SDK 全体でなく MessagesClient に依存 | SDK の型を直接使う | モックを数行にする |

## 6. リスク

| # | リスク | 気づき方 | 起きたときの対応 |
| --- | --- | --- | --- |
| R1 | 同じエラーの修正が堂々巡りする | 同一テストの失敗が3回続く | **止めて報告**（CLAUDE.md 停止条件） |
| R2 | 仕様に無い判断が必要になる | spec.md に該当箇所が無い | **止めて質問**。推測で進めない |
| R3 | テストを実装に合わせて緩める | 期待値の変更が差分に混ざる | CLAUDE.md で禁止＋終了後の差分レビュー |
```

**一気通貫向けに効いている書き方**（すべて `2-3-7` で学んだことの適用です）：

| 書き方 | なぜ一気通貫で効くか |
| --- | --- |
| **1タスク＝1コミット**の粒度 | 途中で止まっても、どこまで進んだかがコミット単位で分かる。失敗したとき戻る位置が決まる |
| 完了条件を**機械が判定できる形**で書く | 逐次型では人が「OK、次へ」と言っていた。一気通貫ではこの欄が代わりに判定する。「きれいに実装できている」のような**人にしか判定できない条件を書くと、そこで自走が止まる**か、エージェントの自己申告で素通りする |
| リスク欄に**停止条件**を書く | 「完成まで走れ」と「おかしくなったら止まれ」はセットで指示する。止まる条件が無い計画は、堂々巡りを何時間でも続ける |
| タスクは順番どおり・依存の内側から | 順番の根拠は [README.md](./README.md) §2 と同じ。**計画に順番が書いてあるから、順番を毎回指示しなくてよい** |

> 📌 **PLANS.md はエージェント自身に更新させます**（`2-3-7`）。
> タスクが終わるたびにチェックを付け、途中の決定を決定事項欄に追記させます。これで**セッションが途中で切れても、次のセッションが PLANS.md を読んで続きから再開できます。**進行状態が会話ログではなくファイルにある、というのが要点です。

## 6. 起動プロンプト ── 1回の指示

**ここまでの準備がすべて済んでいれば、セッションで打つ指示はこれだけです。**

```
PLANS.md に従って、T1 から T10 まで順番に実装を進めてください。

- 各タスクの完了条件を満たし、./scripts/verify を緑にしてから
  次のタスクへ進むこと。
- タスクが終わるたびに、PLANS.md のチェックボックスを更新し、
  1タスク1コミットでコミットすること。
- CLAUDE.md の停止条件に当たったら、そこで止めて状況を報告すること。
- すべて終わったら、T10 の突き合わせ表と、未達・保留があれば
  その一覧を報告してください。
```

**このプロンプトが短いのは、内容が薄いからではありません。**逐次型でプロンプトに書いていたこと（順番・基準・ルール・確認方法）が、全部ファイルに移してあるからです。プロンプトに残っているのは「**開始の合図**」「**進行の作法（verify・チェック更新・コミット）**」「**終了時の報告形式**」だけです。

| 起動プロンプトの行 | 支えているファイル |
| --- | --- |
| 「PLANS.md に従って T1 から」 | PLANS.md（順番と完了条件） |
| 「verify を緑にしてから次へ」 | `scripts/verify`（入口）＋ package.json（判定器）＋ settings.json の `allow` |
| 「停止条件に当たったら止める」 | CLAUDE.md（停止条件）＋ PLANS.md（リスク欄） |
| （書いていないが守られる）キー・範囲・テスト改変の禁止 | CLAUDE.md ＋ settings.json の `deny` |

## 8. 環境変数の設定 ── 手動確認と公開の前に

**ここまで環境変数が一度も出てこなかったのは、書き忘れではありません。**実装とテストのループは、判定器がモックで完結しているため、**キー無し・0円で最後まで走ります**（§4）。キーが要るのは、人の作業である**手動確認（§9 の手順5）と公開**の2場面だけです。

> ⚠️ **キーの設定は、エージェントに任せず人がやります。**
> §3-3 の `deny` により、エージェントは `.env.local` を読めません（読ませない設定を自分で入れました）。**「.env.local を作ってキーを設定して」という指示は、この構成では成立しませんし、成立させてはいけません。**キーが会話ログに残るからです（`2-4-11` の漏洩経路）。

### 8-1 必要な環境変数の一覧

このアプリが使う環境変数は1つだけです。

| 変数名 | 用途 | 読む場所 | 取得先 |
| --- | --- | --- | --- |
| `ANTHROPIC_API_KEY` | Anthropic API の認証 | `app/api/summarize/route.ts`（**サーバー側のみ**） | Anthropic Console で作成（`2-4-10`）。**作成時に一度しか表示されない** |

**`NEXT_PUBLIC_` を付けた変数にキーを入れてはいけません**（`2-4-11`）。ビルド時にブラウザへ配られます。

### 8-2 `.env.local` の作成 ── テンプレートからコピーする

リポジトリ直下に **[.env.example](../../.env.example)**（値の入っていないテンプレート）を置いてあります。**テンプレートはリポジトリに入れてよく、実際の値を書いた `.env.local` は入れない**、という分担です。

```bash
cp .env.example .env.local
```

```bash
# .env.local  ← このファイルはリポジトリに入れない
ANTHROPIC_API_KEY=〔Console で作ったキー〕
```

**書いたら、リポジトリに入らないことを必ず確認します**（`2-4-11`）。

```bash
git check-ignore -v .env.local
```

`.gitignore:〔行番号〕:.env*.local` のように出れば除外されています。**何も出なければ危険です。**コミットする前に `.gitignore` を直してください（一度コミットすると履歴に残ります）。

### 8-3 起動の手順 ── 既定は Docker、ホスト直接は任意

`.env.local` を作ってあれば、キーについて追加の操作はありません。

| 起動方法 | キーの読まれ方 |
| --- | --- |
| `./scripts/dev`（**既定**。中身は `docker compose up`） | `compose.yaml` の `env_file` が `.env.local` を読み、コンテナに渡す |
| `npm run dev`（ホストで直接・**非推奨・旧手順**） | Next.js が `.env.local` を自動で読む |

どちらも置き場所は `.env.local` の1か所です。**シェルの `export` やコマンドラインにキーを直接書く方法は使いません**（コマンド履歴に残ります）。

#### 既定の起動 ── Docker

**このサンプルは、ホストに Node.js も `node_modules` も入れない方針です。**依存はコンテナ内の名前付きボリュームにだけ入っているため、**ホストで `npm run dev` を打つと `next: command not found` や `Cannot find module` の類いで失敗します。これは異常ではなく、この構成の既定の状態です。**

```bash
docker compose build     # 初回のみ。依存の取得（npm install）を含む
./scripts/dev            # コンテナ内で開発サーバーが起動する（中身は docker compose up）
```

1. 起動ログに `Ready` 系の表示が出たら、**ブラウザで http://localhost:3000 を開く**
2. 議事録を貼り付けて1回要約し、要約が返ればキーは通っています
3. 終了は **Ctrl+C**。コンテナを片付けるときは `docker compose down`

検収（§9）の判定器も同じく Docker 経由で回します：`./scripts/verify`

#### ホストで `npm run dev` したい場合（非推奨・旧手順）

**非推奨の旧手順です。**ホストに Node.js と `node_modules` が入るため、「ホストに入れない」というこのサンプルの方針（[`minutes-app/README.md`](../../README.md) 冒頭「実行は Docker の中で行います」）からは外れます。Docker が使えない事情がある場合に限り、それを理解したうえで行ってください。

1. **Node.js を用意する。**コンテナと同じ **Node.js 22 系**（`Dockerfile` の `node:22`）を推奨。Next.js が要求するバージョンは変わることがあるため、[Next.js 公式の動作要件](https://nextjs.org/docs/app/getting-started/installation)を確認してください（参照日 2026-08-28）
2. **依存をホストに入れる**：`npm install`（`node_modules/` がホストに作られます。`.gitignore` 済みなのでコミットには入りません）
3. **起動する**：`npm run dev` → ブラウザで http://localhost:3000 を開く

> 💡 **あとで Docker に戻っても衝突しません。**
> コンテナは名前付きボリュームの `node_modules` を使い、ホスト側のものは見ません（`compose.yaml` のコメント参照）。ホストを元の状態に戻したいときは `rm -rf node_modules` で削除します。

### 8-4 Vercel への環境変数の登録 ── 公開まで進める場合

デプロイは PLANS.md のスコープ外ですが、公開するときの手順を載せておきます（`2-5-16`。**§3-3 の `ask: Bash(vercel *)` により、デプロイ操作は承認制です**）。

1. Vercel の **Settings → Environment Variables** で `ANTHROPIC_API_KEY` を登録する（項目の名前と場所は変わることがあります。**画面表示を正としてください**）
2. **Production に適用されているか**（チェックが入っているか）を確認する
3. **登録した「あと」に再デプロイする。**登録前のデプロイには反映されていません。**「登録したのに動かない」の大半はこれです**
4. 公開 URL で1回動かして反映を確かめる。失敗したら Vercel の Functions ログを見る ── `failureKind` が `api_error` で `attempts` が1のまま即失敗なら、キーの未設定・値違い・失効です（`2-5-16`）
5. **公開ページの JavaScript に `sk-ant` が無いことを検索で確認する。**ヒットしたら、そのキーは失効させて作り直します（`2-4-11`）

> 📌 **Ready（緑）は「ビルドが通った」という意味だけです**（`1-2-8`）。
> 環境変数が入っているかどうかは、この表示では分かりません。**公開 URL で1回動かすまで、反映は確認できていません。**

## 9. 終わった後、人がやること ── 「完成しました」を検収する

**一気通貫で自動化したのは実装のループであって、確認ではありません。**終了報告が来たら、受託の検収と同じ手順で確かめます。

| 順 | やること | 対応する節 |
| --- | --- | --- |
| 1 | `git diff --stat` で**変更されたファイルの一覧**を見る。頼んでいない場所が変わっていないか | `2-5-15` 3-4（差分レビュー） |
| 2 | `package.json` の差分を見る。**依存が増えていたら理由を確認**する | `2-5-15` |
| 3 | テストの差分を見る。**期待値が緩められていないか** | `2-5-15`・Constitution 第14条 |
| 4 | T10 の突き合わせ表を、**spec.md を上から読みながら自分の目で**埋め直す | Constitution 第14条1 |
| 5 | アプリを起動して手動確認（空入力・正常系・通信失敗の3つ）。起動は §8-3 のとおり、既定は `./scripts/dev` → http://localhost:3000 | [README.md](./README.md) ステップ9 |

> ⚠️ **verify の緑と、エージェントの「完成しました」は、合否の判定ではありません**（Constitution 第13条8）。
> 緑が意味するのは「書いたテストの範囲で確かめた」まで、報告が意味するのは「本人はそう思っている」までです。**合否を決めるのは spec.md との突き合わせであり、それをやるのは人です。**ここを自動化の対象にした瞬間、`2-1-2` で見た「自信満々のまま誤ったものを量産するループ」になります。

## 10. うまく走らないときの切り分け

**症状は必ず、どれかのファイルの不備を指しています。**エージェントを責める前に、こちらの設定を疑います。

| 症状 | 不備があるファイル | 直し方 |
| --- | --- | --- |
| 質問ばかりで進まない | `docs/spec.md` | 仕様の抜け。質問された箇所を spec.md に書き足す |
| 確認プロンプトだらけで止まる | `.claude/settings.json` | `allow` が足りない。判定器と状態確認を allow に入れる（止めすぎは外される・`0-2-5`） |
| 頼んでいないファイルが変わる | `CLAUDE.md` | 「変更の範囲」（一覧を出す・一覧外は変えない）が無いか、弱い |
| テストを緩めて緑にしてくる | `CLAUDE.md`＋終了後レビュー | 「触ってはいけないもの」に明記し、差分レビューで検知する |
| 同じエラーで回り続ける | `PLANS.md`・`CLAUDE.md` | 停止条件（同じエラー3回）が書かれていない |
| 「完成」の中身が仕様とずれている | `PLANS.md` | 完了条件が機械で判定できる形になっていない（自己申告で素通りしている） |

## 11. まとめ ── 逐次型から一気通貫型へ

| | [README.md](./README.md)（逐次型） | この文書（一気通貫型） |
| --- | --- | --- |
| 指示の回数 | 部品ごと（11回） | **1回** |
| 順番・基準・ルールの置き場所 | 毎回のプロンプト | **リポジトリ内のファイル** |
| 進んでよいかの判定 | 人が毎ステップ | **完了条件＋判定器** |
| 人の仕事 | 各ステップの指示と確認 | **事前のファイル整備と、事後の検収** |
| 向いている場面 | 初めて作る・型を学ぶ | 型が手に馴染んだあと・2回目以降 |

**順番を守ってください。最初から一気通貫はやらないでください。**逐次型を1周やっていないと、§10 の切り分け（症状からファイルの不備を特定する）ができません。**自動で回る仕組みは、手で回したことのある人にしか直せません。**
